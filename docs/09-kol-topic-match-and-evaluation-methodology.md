# KOL × 話題 Match 與導流素材前後評估方法論

**版本：** v2.0（依 [`docs/10` 簡化提案](10-dashboard-simplification-proposal.md) 與其外部 review 重寫）
**制定日期：** 2026-08-19
**適用範圍：** `dashboard/` 儀表板的所有計算；`kols/*/topic_affinity.json` 的資料標準
**性質：** 可執行規格——本文件的每一條公式都對應 `dashboard/server/lib/scoring/` 裡的一個函式。
改了公式就要改程式，改了程式就要回來改這裡。

> **這份文件回答三個問題：**
> 1. 一個 KOL「可以發揮的屬性」怎麼被量化？（§1–§2）
> 2. KOL 與話題的 Match 程度怎麼算？（§3）
> 3. 導流素材發布前怎麼定目標、發布後怎麼回收、兩者怎麼對照？（§4）
>
> 與 [`06` Part D](06-viral-content-framework-and-four-axis-judgment.md) 的四維判準**分工明確**：
> 四維判的是「這支片做得好不好」（成片品質），本文件判的是「這個題目該不該由這個人做」（題材配置）。
> **四維不是開工門檻**，它是發片前的檢查清單。

## §0 四個底層原則

### 原則一：KOL 與話題必須用同一套座標

不能用形容詞描述 KOL（「知性」「溫暖」），再用另一套形容詞描述話題（「熱門」「爭議」），
然後靠感覺配對。兩邊必須**投影到同一組軸**上，Match 才能算，也才能被質疑與修正。

### 原則二：分數要能回溯到原始文件

`topic_affinity.json` 的每一軸都附 `why`，指出這個分數是從 `profile.json` 的哪一句推出來的。
**沒有 `why` 的分數視為未定義**，不可進入計算。

### 原則三：門檻歸門檻，分數歸分數

紅線不是「扣幾分」的問題，支柱歸屬也不是。凡是「是或不是」的判斷一律做成 **gate**，
不要塞進加權公式裡假裝它是連續的。v1 讓紅線同時佔 10% 權重又有 veto 特例，
等於同一件事寫了兩遍。

### 原則四：顯示可以少，儲存不能少

砍掉一條公式隨時可以重寫；砍掉「不再儲存某個實際欄位」，等有資料時就永久補不回來。
後評的原始欄位**全部儲存**，UI 只呈現其中三個。

## §1 四軸屬性向量（Attribute Axes）

定義在 `kols/topic-axes.json`，KOL 側資料在 `kols/{id}/topic_affinity.json` 的 `axes`。

| 軸 | key | 這一軸在問什麼 | 由 v1 哪兩軸合併 |
|----|-----|--------------|----------------|
| 理性拆解 | `analysis` | 能不能把事情拆成規則／機率／設計邏輯，並打破常識直覺 | 理性拆解 + 反直覺衝突 |
| 敘事情緒 | `story` | 能不能講成有人物與弧線的故事，並讓觀眾「被說中」 | 敘事張力 + 情緒共鳴 |
| 視覺張力 | `visual` | 場景、光影、空間資訊量撐不撐得起，以及隨之而來的嚮往感 | 視覺表現 + 嚮往感 |
| 身分可信 | `credibility` | 有沒有身分／實績／長期積累背書。**唯一無法靠製作補的軸** | — |

分數範圍 0–100。**不要把每個人都打成 80 分以上**——沒有低分軸的向量無法區分人選，
等於沒有資訊。實務上每位 KOL 應該有 1–2 軸落在 60 以下。

### 1.1 `format_fit` 日常適配：存在，但不計分

`format_fit` 記錄這位 KOL 的日常感／可複製／隨手記錄程度。
**它不進 Match 公式**——它影響的是「怎麼拍」，不是「選什麼題」。
它出現在作業流程 (c) 的素材企劃提示裡，用來判斷這題適不適合做成隨手感切角。

### 1.2 話題側的軸需求（axis_demand）

兩種取得方式，優先序由上而下：

1. **領域預設**：套 `topic-axes.json` 的 `domain_axis_demand[domain]`。**這是常態。**
2. **手動覆寫**：`topic_hooks[].axis_demand`。**預設不要填**，只有當這個連結點明顯偏離
   domain 平均時才用（例如同為 `movie` 但這題是純情緒故事）。

> v1 還有第三種：依 Tag 關鍵字對個別軸加減分（`+15` analysis、`+18` emotion…）。
> 那些數字是編的，0 筆實績下沒有東西可以校準它們——已移除。

## §2 建模素材屬性（Material Attributes）

`topic_affinity.json` 的 `material_attributes` 只留三個欄位：
`generation_model`、`consistency`、`usable_formats`。
視覺語言與色盤**不放這裡**——直接讀 `profile.json` 的 `content.aesthetic`，避免同一件事兩處維護。

這一段不進 Match 公式，但進**可執行性檢查（Feasibility Gate）**：
如果一個話題最佳表現形式是「多場景敘事長片」，而該 KOL 只有 3 張身分參考圖、沒有 Reference Element，
Dashboard 會在素材企劃階段標示風險，而不是等生成失敗才發現。

## §3 Match 分數（KOL × 話題）

### 3.1 四個計分維度與兩個 Gate

```
分數 = 0.35·personaFit + 0.30·pillarFit + 0.20·topicHeat + 0.15·regionFit

Gate 1（紅線）：severity=block 命中 → 不進推薦清單，只出現在「已排除」並附原因
                severity=warn  命中 → 照常排序，列出警告，不扣分
Gate 2（支柱）：所有支柱覆蓋率皆為 0 → 狀態 needsBinding，不給 A/B/C/D 等級
```

| 維度 | 算什麼 | 資料來源 |
|------|--------|---------|
| `personaFit` 人設契合 | KOL 四軸向量與話題軸需求的加權重疊 | `axes` × `axis_demand` |
| `pillarFit` 支柱覆蓋 | 話題落得進哪個內容支柱，用支柱權重加權 | `profile.json content.pillars` + `pillar_keywords` |
| `topicHeat` 話題熱度 | 量體與成長率的合成分數 | Apify（Threads / TikTok / IG） |
| `regionFit` 地區契合 | 話題地區、語言與 KOL 覆蓋範圍的重疊 | `reach.regions` / `reach.language` |

### 3.2 personaFit：需求加權的達成率

單純的餘弦相似度會讓「兩邊都低」也算高分。所以採用**需求加權的達成率**：

```
personaFit = Σ_i ( w_i · min(kol_i / max(demand_i, 1), 1) ) / Σ_i w_i × 100
其中 w_i = demand_i / 100      （需求越高的軸，權重越大）
```

語意是：**話題要求越高的軸，越要看 KOL 在那一軸夠不夠**；
KOL 在話題不需要的軸上再高，也不加分。這避免了「全才假象」。

### 3.3 pillarFit：關鍵字覆蓋 × 支柱權重

對每一根支柱，計算話題與「支柱名稱＋描述＋`pillar_keywords`」的覆蓋率 `cov`，取：

```
pillarFit = max_p ( min(cov_p × 2.5, 1) × (0.6 + 0.4 · normalizedWeight_p) ) × 100
```

**三個實作上必須處理的細節：**

1. **簡繁與中英混排。** 支柱名稱與描述多為繁體或英文，話題多為簡體。
   比對前一律轉成簡體（`dashboard/server/lib/text.js`），否則「概率」永遠對不上「機率」。
2. **CJK 沒有詞界。** 整句比對太嚴、單字比對太鬆，一律取**二元字組（bigram）**；
   英文取 3 字以上的詞並去停用詞。短英文 tag 必須做詞界比對——否則 `ai` 會命中 `daily`。
3. **`pillar_keywords` 是必要資料，不是加分項。** 命中宣告關鍵字時 `cov` 下限拉到 0.7。
   **關鍵字要具體**——「判斷」「選擇」「故事」這類泛用詞會讓所有支柱都命中，等於沒有支柱。

**綁定支柱不再有保底分。** `topic_hooks[].pillar` 指定的支柱會標記 `bound: true`，
但**分數照算**。v1 給它 70 分下限，導致編輯一綁定就繞過整個 scoring。

**無支柱對應 → `needsBinding`，不給等級。** v1 在這裡套一條封頂曲線
`min(raw, 54 + 0.1·raw)`——那條曲線沒有任何依據，犯的是與漏斗預測相同的毛病。
現在它是一個明確狀態：**這個題目在這個帳號上沒有家，先決定它屬於哪根支柱**。

### 3.4 topicHeat：兩個訊號

```
topicHeat = 0.60 · log 標準化(volume) + 0.40 · 標準化(growth)
```

**先講清楚這兩個數字實際上是什麼**（2026-08-19 以真實 token 實跑後確認）：

Threads / TikTok / Instagram 的 actor **全部只回傳貼文**，沒有任何一個提供
「這個 tag 被用了 N 次」這種平台級彙總。所以本系統的地區榜是：
**抓各地區種子詞的近期貼文 → 統計貼文裡實際出現的 hashtag**。因此——

| 欄位 | 實際語意 | 不是什麼 |
|------|---------|---------|
| `volume` | 使用該 tag 的**不重複帳號數**（本次取樣內） | 不是平台總聲量 |
| `postCount` | 該 tag 出現的貼文則數 | — |
| `growth7d` | 該 tag 的貼文有多少比例來自**最近 48 小時** | 不是週成長率——沒有 actor 提供 |

API 回傳 `volumeMeaning`（`sample_frequency` / `platform_volume`）讓 UI 據此改標籤，
**不能一律叫「量體」**。

**已知的方法論限制（Gemini review 指出，暫不修但要知道）：**

種子詞決定了探索邊界。TW 用「台灣／taiwan／台北」當種子，聚出來的其實是
**「與台灣一詞共現的 hashtag 榜」**，不是「台灣的熱門話題榜」——一個真正爆紅但沒有加地理 tag
的在地事件（例如某次地震、某部劇）根本不會被抓到。這是倖存者偏差，改不掉，
只能靠擴充種子詞緩解，且擴充會改變榜單的語意。**用這份榜單時要記得它的定義。**

另外樣本量約 300 則，切給上百個 tag 之後，入榜話題的帳號數多半落在 2–5 之間，
名次差異有相當比例是雜訊。**把它當「這幾天大家在講什麼」的粗略掃描，不要當精確排名。**

三個影響排序品質的實作決定：

1. **種子字必須排除。** 搜 `#singapore` 的結果每一則都含 `#singapore`，
   不排除的話排行榜前幾名就是自己查詢的鏡子。
2. **算帳號數而非貼文數。** 一個 tag 被同一帳號用 14 次是那個帳號的發文習慣；
   被 14 個帳號各用一次才是趨勢。實測中 `#北海道/#北海道冬天/#旅行旧照` 同時 14 分
   就是同一個帳號的 tag 區塊造成的。
3. **平台通用字要濾掉**（fyp / foryou / viral / reels、以及中文的推薦／熱門／流量密碼等）——
   它們每批都在前面，不帶題材資訊。純英文名單擋不到區域型流量字，兩邊都要列。
4. **小樣本不算成長率。** 一個 tag 只有 2 則貼文、剛好都在 48 小時內，就會拿到 100% 而衝上榜首。
   低於 3 則時 `growth7d` 回 `null`（標準化後視為中性 50），不讓雜訊拿滿分。
5. **跨平台合併要用量體加權，而且只算一次。** 原本邊合併邊兩兩平均，
   `((a+b)/2 + c)/2` 會讓最後一個平台拿到一半權重，同一組數字換個順序結果就不同。

- `volume` 用對數標準化，因為長尾分布下線性標準化會讓前一兩名吃光分數。
- 兩個訊號都取當次查詢結果集內的相對位置（min–max），所以 `topicHeat` 永遠是
  「在這批話題裡的相對熱度」。
- **互動率已移除。** 多數 actor 不回傳可用的曝光基數，硬算會退化成常數 50。

### 3.5 regionFit：為什麼它必須計分

```
regionFit = 60 · regionOverlap + 40 · languageMatch
```

`regionOverlap` 依 `reach.regions` 的排序給遞減權重（第一順位 = 1.0，第二 = 0.85…）；
`languageMatch` 為 1 / 0.5（同語系不同字體，如 zh-Hans vs zh-Hant）/ 0。

> **這一項曾經被提議改成純標示，那是錯的。** 在方向 (a)「KOL → 話題」，
> 同一份地區清單裡所有話題地區相同，它確實對排序沒有貢獻。
> 但方向 (b)「話題 → KOL」是**一個話題比五位 KOL**，而他們的 `regions` 與 `language` 完全不同
> ——地區在那個方向正是排序差異的來源。砍掉它，語言不合的人會排到前面。

### 3.6 分級

| 狀態 | 等級 | 建議動作 |
|------|------|---------|
| 紅線 block 命中 | ✕｜否決 | 不論分數 |
| `needsBinding` | —｜待綁定 | 沒有支柱對應，先綁定支柱再判 |
| ≥ 80 | A｜強配 | 直接排進製作 |
| 65–79 | B｜可做 | 需要一個明確的切角才開工 |
| 50–64 | C｜勉強 | 只在缺題時使用，且要補足最弱的那一軸 |
| < 50 | D｜不建議 | 換人或換題 |

## §4 導流素材前後評估

### 4.1 預先評估：設定目標，不做預測

**v1 做的事：** 從一個 `assumed: true` 的基準值，乘上 `lift = 0.7 + 0.6·(Match/100)`，
再乘 `heatMultiplier = 0.85 + 0.3·(熱度/100)`，往下推五層漏斗。

**為什麼拿掉：** 那兩個乘數是編的。沒有任何資料支持 Match 90 分會比 50 分多帶 30% 觸及。
五個看起來精確的數字全建在兩個沒有來源的係數上——**這比不預測還糟**，
因為它讓人以為系統知道一些它其實不知道的事。

**現在的預評由三塊組成：**

1. **配置分數** — §3 的 Match 分數與等級，決定「該不該由這個人做這題」。
2. **兩個目標** — 企劃者自己填的**目標觀看**與**目標外連點擊**。
   人填的目標比假公式算的預測有用：它逼企劃者說出「這支我期待什麼」，
   事後對照的是**一個人做過的判斷**，不是一個係數。
3. **四維檢查清單** — `06` Part D 的娛樂性／音樂性／真實性／動作流暢性，1–5 分。
   發片前要跑，未達 4 分要修，但**不擋開工**——它判的是成片品質，不是選題配置。

決策狀態：`blocked`（紅線）／ `unbound`（待綁定支柱）／ `reassign`（Match < 50）／
`needs_target`（還沒填目標）／ `go`（可開工）。

預評結果存成一筆記錄，含 `matchSnapshot`——**必須存快照**，
否則之後話題熱度變了，就無法做誠實的對照。

### 4.2 後續評估：全存，顯示三個

素材發布後，從 **Match 庫**（`match_records`）抓回實績。

**儲存的欄位（全部）：**
`views` `reach` `impressions` `likes` `comments` `shares` `saves`
`profileVisits` `linkClicks` `conversions` `follows` `avgWatchTime` `completionRate`
＋衍生的 `engagements` 與 `engagementRate`。

**顯示的欄位（三個）：** 觀看、互動、外連點擊。

> 為什麼不乾脆只存三個：這些**不是預測，是當下就拿得到的事實**。
> 存起來幾乎不花成本，砍掉就永遠回不來——50 筆之後想分辨「完播差」與「CTA 差」，
> 沒有 `completionRate` 就永遠分不出來。

### 4.3 對照分析：三列 ＋ 一句歸因

```
variance = (實際 − 目標) / 目標
達標門檻：variance ≥ −15%
```

歸因只有兩條規則：

- **觸及達標、點擊不足 → 素材問題**（CTA / 結尾設計）
- **觸及不足 → 選題或發布時機問題**（不是素材本身）

兩者皆達標即「符合預期」；缺目標值則回報「目標不完整」，不硬猜。

### 4.4 校準迴圈：目前沒有

v1 有一套校準機制（Pearson 相關係數、每位 KOL 的建議基準值），
**要 10 筆完成後評估才會啟動，而目前有 0 筆**——它唯一的作用是在畫面上顯示「樣本 2 / 10」。
已移除。

因為 §4.2 保留了全部原始欄位，**這一刀是可逆的**：
等真的累積到 10 筆、且有人真的想調參數時再寫，那時候資料是齊的。

## §5 三條作業流程（Workflow Directions）

| 方向 | 輸入 | 輸出 | 使用時機 |
|------|------|------|---------|
| **(a) KOL → 話題** | 一位 KOL | 該地區前十大話題依 Match 排序 ＋ 該 KOL 的自有連結點 | 這個人這週該做什麼 |
| **(b) 話題 → KOL** | 一個話題／Tag | 全部 KOL 依 Match 排序 | 這個熱點該派誰上 |
| **(c) 組合 → 素材** | KOL × 1–3 個話題 | 素材企劃骨架 ＋ 預評分數卡 | 決定了人與題，要開工 |

**交叉查詢（Cross-query）** 是 (a)(b) 的共同底層：多個 Tag 之間做交集。
實務上最有價值的是**兩個 Tag 的交集**——單一 Tag 太大（人人都能做），三個以上通常無資料。

方向 (c) 產出的素材企劃骨架只有五欄：**綁定支柱 / 建議格式 / 可用場景 / 視覺語言 / 待填的鉤子與 CTA**，
外加可執行性提示（含 `format_fit` 的切角建議與紅線警告）。
**它是給企劃者填的骨架，不是自動生成的成品文案。**

## §6 資料流總覽

```
kols/{id}/profile.json ─┐
kols/{id}/topic_affinity.json ─┼─→ KOL Repository ─┐
kols/topic-axes.json ───┘                          │
                                                   ├─→ Match Engine (§3) ─┬─→ (a) KOL→話題
Apify (Threads / TikTok / IG) ─→ Topic Source ─────┘                      ├─→ (b) 話題→KOL
                                                                          └─→ (c) 組合→素材企劃
```
