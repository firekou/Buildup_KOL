## §0 這份規格的紀律

1. **只有 `99-verification.md` 標記 ✅ 的文獻可以進入 Zone A。** 未驗證的一律進 Zone B，且預設關閉。
2. **不新增任何沒有出處的數字。** 現行 `WEIGHTS = 0.35/0.3/0.2/0.15` 是編的；**我們不會用另一組編的數字取代它**——包含編的**公式**（v1.0 的 `3/n` 就是犯了這一條）。
3. **每一個會影響決策的數字，畫面上都必須能看到它的意義、影響度與依據。**
4. **【v1.1 新增】任何維度只要有「低到不可接受」的語意，它就必須是 gate，不能只是平均數裡的一項。**
   → 這條直接來自兩位共同的批評：`mean()` 仍然是線性補償模型。
5. **【v1.1 新增】任何會讓某類案例永遠無法被觀測的設計，都是禁止的。**
   → 倖存者偏差。我們在 `93` 批評過 `match.score < 50 → reassign`，v1.0 用 `FLOOR → VETO` 犯了同一個錯。

### 兩個貫穿全案的方向判斷（使用者裁示）

- **Gemini 的批判為主軸。**
- **心理量表派為評分主體。** 結構中心性派與擴散實證派**不進評分**，只作為約束與警示。

## §1 三區架構

| 區 | 名稱 | 內容 | 預設 | 能否影響決策 |

### 1.1【v1.1 修正】Zone B 的隔離改為「無法選擇污染」

v1.0 寫的是「使用者打開開關時跳確認：你確定要讓它影響排序嗎？」——**兩位都指出這直接違反了表格裡的「❌ 否」**，而且定錨效應會讓看到數字本身就構成污染。

**v1.1 的隔離規則（三條，皆可驗收）：**
1. Zone B **只存在於獨立的 `/sandbox` 分頁**，不出現在主決策畫面
2. Zone B **不得改變主候選清單的排序**，也不得被 `/api/plans/generate` 讀取
3. 未達出 B 條件前，**不計算也不顯示具體數值**——反灰並標示「資料累積中（目前 N 筆 / 判準未達成）」

## §2 Zone A · 新的評分模型

### 2.1【v1.1 重構】四個階段，前兩階段不算分

v1.0 把「資料驗證」和「內容適配」混在同一個 gate 引擎裡。兩位都指出這是職責不清。

```
階段 0  VALIDATION（不是 gate，是表單驗證，連算都不該算）
  ├─ V1  軸缺 why 或非數字                → needs_input（回 wizard 補件）
  ├─ V2  缺 credibility_mode              → needs_input
  └─ V3  無內容支柱可歸屬                  → needs_binding（人工綁定後重算）

階段 1  GATES（內容適配，不可補償，任一不過即停）
  ├─ G1  Zone C block 級紅線命中           → VETO
  ├─ G2  可信度型態不符                    → VETO
  │      （話題需要具身主張，但 KOL 是資料庫型；或反之）
  └─ G3  fit < FLOOR                      → VETO ／ EXPERIMENT（見 §2.4）

階段 2  篩選分（三維等權，只在 gate 全過後計算）
  screeningScore = mean(fit, pillar, homophily)
  ※ credibilityMode 已上移為 G2，不再是平均數裡的一項
  ※ topicHeat 不在其中

階段 3  時機（並列顯示，永遠不進總分、不進 gate）
  timing = { heat, heatConfidence, caveat }
```

### 2.2【v1.1 修正】`credibilityMode` 從維度上移為 Gate

Gemini 的原話：「你把二元屬性分類的 `credibilityMode` 和連續屬性的 `fit` 放進同一個算術平均數裡，這兩者的數值變異數完全不同。」

**這是對的，而且問題比變異數更根本：可信度型態不符是一個「是或否」的事實，不是一個程度。** 一個資料庫型 KOL 被指派了需要親身經歷的題目，這不是「扣分」，是「不能做」。

→ 上移為 **G2**，與 `R-EMBODIMENT` 共用同一份判定（避免 GPT 指出的「兩套具身判定漂移」）。

### 2.3【v1.1 修正】剩下三維：等權 ＋ 各自的地板

兩位都指出 `mean()` 仍是線性補償——`fit` 高可以補 `homophily` 低。依 §0 紀律 4：

| 維度 | 地板 | 低於地板時 |
|---|---|---|
| `fit` | `FLOOR`（G3） | VETO 或 EXPERIMENT |
| `pillar` | 0（無支柱歸屬） | 已由 V3 攔截 |
| `homophily` | **無地板** | 低分照實顯示，不否決 |

`homophily` 為什麼沒有地板：Lou & Yuan 2019 ✅ 確立它是信任的**前因之一**，但**沒有任何文獻說它有一條不可跨越的底線**。編一條就是犯紀律 2。
→ 它低分時的處理是**在 UI 上把它單獨標紅並寫出後果**，而不是靜悄悄被平均掉。

### 2.4【v1.1 核心修正】底線校準悖論

**Gemini 的第一名危險：**
> 如果 G3 把 `fit < 30` 直接 VETO，這些企劃就永遠不會上線。既然無法發布，你絕對收不到這區間的真實成效資料，所謂「保留 borderline 作為校準來源」根本是空話。

**這是對的，而且是我自己在 `93-account-system.md` 批評過的同一個錯誤**（`match.score < 50 → reassign` 會使倒 U 假說不可識別）。v1.0 換了個名字重犯一次。

**修正：G3 分成三段，不是兩段。**

| `fit` 區間 | 狀態 | 行為 |
|---|---|---|
| `< FLOOR − 10` | `VETO` | 不予產製。**但強制寫入 `vetoLog`，含人工覆核欄位** |
| `FLOOR ± 10` | **`EXPERIMENT`** | **允許產製與發布**，強制標記為 `experimentBand`，並佔用實驗配額 |
| `> FLOOR + 10` | `PASS` | 正常流程 |

**`EXPERIMENT` 帶的三個規則：**
1. 產出的企劃**必須**帶 `experimentBand: true`，發布後的成效記錄同樣帶此旗標
2. 佔用**實驗配額**——每批產出中允許的實驗帶數量由人決定並記錄，系統不自動決定比例（避免又編一個數字）
3. UI 明說：「這一則的人設契合落在我們自己畫的底線附近。**我們讓它上線，是為了知道這條線畫得對不對。**」

**`vetoLog` 的欄位：** `kolId`、`topicId`、`fit`、`gatesFailed`、`reviewedBy`、`reviewedAt`、`humanVerdict`（`agree` / `disagree` / `unsure`）、`note`。
→ 沒有這個，被否決的案子連「人覺得這個否決對不對」都收不到。GPT 的原話：「否則校準資料會有嚴重選擇偏誤。」

### 2.5【v1.1 修正】`screeningScore` 降格為分帶，不顯示精確數字

GPT：「UI 不應顯示成 71.2 這種精確預測感，改用區間或等級會比較一致。」

**採納。** 內部保留數值供排序，**UI 只顯示分帶**：

| 分帶 | 意義 |
|---|---|
| 高 | 三維都在中上，沒有明顯短板 |
| 中 | 有短板但沒有低於地板 |
| 低 | 勉強過 gate |
| 實驗 | 落在 `EXPERIMENT` 帶 |

分帶旁邊永遠並列三根維度長條，**點開就是 §3 的備註**。

### 2.6【v1.1 刪除】M3「支柱 > 3 時分數乘以 3/n」

**兩位共同判定為「用新編造的算式取代舊編造的數字」。這個判定是對的。**

Zuckerman 1999 ✅ 只說「身分歸類不清會被市場折價」，**沒有給出 3 這個上限，更沒有給出線性反比的懲罰函數**。GPT 另外指出一個實質後果：「4 根很清楚的支柱會被硬砍，2 根但關鍵字很泛反而可能逃過。」

→ **從 Zone A 評分中完全移除。** 保留為 `W-BLURRED-PILLAR` 警示（Zone C），由人判斷。

`pillarFit` 保留的兩項修正（M1／M2）不受影響，因為它們是**移除既有的假訊號**，不是新增假訊號：
- **M1** 刪除過度泛用的 `pillar_keywords`（`人生／职场／内耗／边界／决定／风险` 等）
- **M2** 移除 `keywordHit` 的 `0.7` 地板 —— 那個地板讓「關鍵字表愈寬愈有利」，方向與 Zuckerman 相反

### 2.7 `FLOOR` 的定位

`FLOOR = 30`，放在 `kols/scoring-config.json`，標 `calibration: "prior"`。

UI 措辭（強制）：
> 這條線目前是**先驗**。文獻（Mandler 1982）確立「有一條線」，但沒說在哪裡。落在這條線附近的案子我們會讓它上線，就是為了知道線該畫在哪。

### 2.8 `topicHeat` 移出總分

依 Gemini Q3 的判詞——現行熱度衡量的是「特定種子詞極小樣本下該詞彙的靜態共現密度」。

- 熱度仍計算、仍顯示，**不進總分、不進 gate**
- `heatConfidence`：`none` / `low` — **永遠不會有 `high`**
  - 無 `topicSnapshots` → `none`，UI 顯示「**無法判定升溫**」而非數字
  - 有足夠快照且通過 §4 B4 的判準 → `low`
- **禁止出現的字：** 「正在紅」「新趨勢」「爆紅」「跨圈潛力」「熱度上升」
- `heatConfidence = none` 時，欄位標籤必須是 **「樣本共現密度」**

### 2.9 熱度分 domain（Romero et al. 2011 ✅）

`classifyDomain()` 已存在但跑在 `scoreHeat()` 之後。**調換順序**，改為同 domain 內 normalize。

```jsonc

  "meaning":  "白話：觀眾覺得「這個人跟我是同一種人」的程度。",

  "evidence": [{
    "claim": "資訊價值、可信賴度、吸引力、與追隨者的相似性，四者正向影響追隨者的信任。",
    "source": "Lou & Yuan (2019), Journal of Interactive Advertising, 19(1), 58–73",
    "url": "https://doi.org/10.1080/15252019.2018.1533501",
    "status": "verified"
  }],
  "failureMode": "選太高：人設沒有專業距離，講什麼都像朋友閒聊，權威感消失。選太低：觀眾會佩服但不會行動。",
  "calibration": "prior"

```

### 3.2【v1.1 修正】`decisionRole` 的定義（取代舊的 `impact`）

| 值 | 意義 | 判準（客觀，不循環） |
|---|---|---|
| `gate` | 單獨就能否決 | 它出現在 §2.1 的階段 1 |
| `score` | 進入 `screeningScore`，會改變排序但不會改變 go/no-go | 它出現在階段 2 |
| `display` | 只顯示，不進任何計算 | 階段 3，或 Zone B |

### 3.3【v1.1 大幅補強】`calibration` 三態

| 值 | 意義 | UI |
|---|---|---|
| `verified` | 有 ✅ 文獻直接支持這個做法 | 綠色，附連結 |
| `prior` | 方向有依據，**具體數字或公式是我們定的** | **黃色，附「這個數字目前是先驗」** |
| `calibrated` | 已通過 §9.4 的校準判準 | 藍色，附樣本數、判準、日期 |

**GPT 的第二名危險：** 「未來會出現『有 30 筆所以藍色』的假校準。」

→ **v1.1 刪除所有固定筆數門檻。** `calibrated` 的取得條件見 §9.4，是**統計判準**，不是計數。

**目前全系統沒有任何一項是 `calibrated`。** 首頁顯示：「已校準項目：0 / N」。

## §5 Zone C · 紅線與警示

【v1.1】**block 由 5 條增為 9 條，warn 重新分級。** 兩位共同指出 v1.0 漏掉了資料庫型人設的對應紅線。

### 5.1 `block` 級

| ID | 規則 | 依據 | v1.1 變更 |
|---|---|---|---|
| `R-EMBODIMENT` | 不得主張不可查證的親身在場／經歷／身體感受 | Sundar 2008 ✅；Lee & Eastin 2021 ✅ | **移除 `applies_when`** — GPT 指出資料庫型 KOL 說「我爬過」一樣該擋，v1.0 的條件寫反了 |
| `R-CREDENTIAL` | 不得宣稱 AI 結構上不可能取得的憑證 | Sundar 2008 ✅ | **`scope` 加 `plan`、`script`** — 企劃裡臨時寫「她是持照嚮導」也要擋 |
| `R-FABRICATED-SOURCE` | **【新增】** 不得捏造研究、報告、路線紀錄、統計數字、新聞事件 | Sundar 2008 ✅ | **兩位共同指出的缺漏。** 資料庫型人設靠「客觀分析與資料」建立信任，捏造來源就是它的具身造假 |
| `R-AI-DISCLOSURE` | **【新增】** 不得假裝是真人，或隱瞞 AI 身分來支撐可信度 | Lee & Eastin 2021 ✅（transparent endorsement） | GPT 提出 |
| `R-REAL-PERSON-IMPERSONATION` | **【新增】** 不得冒充真實人物、機構職位或可查證的從業者 | — | GPT 提出，比 `R-CREDENTIAL` 更廣 |
| `R-HIGH-STAKES-ADVICE` | **【新增】** 醫療／金融／法律／人身安全，不得給確定性的個案指令 | Friestad & Wright 1994 ✅ | GPT 提出。我們有登山安全與投資兩個人設，這條是實質需要的 |
| `R-HATE-HARASSMENT` | **【新增】** 不得貶低受保護或易受害群體 | — | 從 `W-OUTGROUP` 拆出（GPT） |
| `R-FAKE-CERTAINTY` | 絕對安全／零風險／保證成功／百分百 | — | **移除「一定會」** — GPT 指出「觀眾一定會問你是不是真的去過」是正當用法 |
| `R-STAGED-DANGER` | 不得為互動率擺拍危險動作 | — | 不變 |

### 5.2 `warn` 級

| ID | 規則 | v1.1 變更 |
|---|---|---|
| `W-ENGAGEMENT-BAIT` | 刻意留破綻／擺反道具換留言 | **理由完全改寫**（見 5.3）。**惡意版本上移為 `R-HIGH-STAKES-ADVICE`／`R-FABRICATED-SOURCE`** |
| `W-OUTGROUP` | 以外團體對立換互動（政治立場層級） | 受保護群體的部分已拆出為 `R-HATE-HARASSMENT` |
| `W-BLURRED-PILLAR` | 支柱過多或關鍵字過泛 | **成為支柱治理的唯一機制**（§2.6 的 `3/n` 已刪除） |
| `W-NO-BASELINE` | 無時間序列時談時機 | 不變 |

### 5.3【v1.1 重要修正】刪除「模型投票」這個分級依據

v1.0 把 `W-ENGAGEMENT-BAIT` 列為 warn，理由寫的是「Gemini 推薦、GPT 與 Claude 反對」。

**兩位都指出這是錯的。** Gemini 的原話最直接：「極度荒謬，這直接打破了 §0 宣稱的『只有 ✅ 文獻可以影響決策』。」

**它們是對的。用哪個模型投了幾票來決定紅線等級，本身就是 §0 紀律 1 的違反。**

**v1.1 的分級判準（四條，客觀）：**
1. 傷害是否**不可逆**
2. 是否構成**欺騙**
3. 是否**違法或危害人身**
4. 文獻證據是否**一致**

依此重新判定「互動誘餌」，並採用 GPT 的拆分——它比 Gemini 的一律 block 更精確：

| 行為 | 等級 | 理由 |
|---|---|---|
| 持有並表達反直覺的立場 | **不列管** | 這只是有觀點。而且它是 `W-ENGAGEMENT-BAIT` 的正當替代方案 |
| 刻意演出小瑕疵／擺反道具換留言 | `warn` | 有欺騙成分但可逆、不危害。Friestad & Wright 1994 ✅：被看穿時傷害的是整個帳號的評價 |
| **故意散布錯誤的安全／醫療／金融資訊來釣留言** | **`block`** | 不可逆 ＋ 欺騙 ＋ 危害人身。歸入 `R-HIGH-STAKES-ADVICE` 與 `R-FABRICATED-SOURCE` |

### 5.4【v1.1 核心修正】關鍵字比對降格為 lint，不是判定

**兩位共同的、最具體的批評。** Gemini：「寫死 `patterns` 是本規格中最偷懶、最糟的設計。」

**假陽性（會擋掉正當用法）：**
- 「我親身比對了三份報告」「我實際測試了三種提示詞模板」← 資料庫型的正當敘述
- 「我走過很多彎路才找到這份資料」← 比喻用法
- 「觀眾**一定會**問你是不是真的去過」← 風險提醒，不是保證宣稱

**假陰性（抓不到的具身敘事，GPT 提供）：**
- 「上次在營地醒來」「那晚我手指凍到沒感覺」「抵達稜線時」

**v1.1 的兩層架構：**

```
第一層  lint（regex / 關鍵字）
  → 產出 candidates，狀態一律是 needs_review，不是 blocked
  → 目的是「不要漏」，容許高假陽性

第二層  語意判定
  ├─ 在 skill 中：由 Claude 依 rule + why_plain 做語意判斷（這是 skill 存在的意義）
  └─ 在 Dashboard 中：needs_review 項目呈現給人確認，不自動否決
```

**唯一的例外**：`R-FAKE-CERTAINTY` 的「絕對安全／零風險／保證成功」等完全無歧義的字串，仍可直接 block。

`rules.json` 因此新增兩個欄位：`detection: "lint" | "exact"`、`semantic_prompt`（給第二層用的判定指引）。

### 5.5 skill 結構

```
.claude/skills/kol-redline-check/
├── SKILL.md              # 含第二層語意判定的操作指引
├── rules.json            # 唯一真實來源，Dashboard 與 skill 共讀
└── check.mjs             # 第一層 lint，回傳 needs_review 清單
```

**`R-NO-WHY` 的定位【v1.1 修正】：** Gemini 指出它是表單驗證、不是內容紅線。**部分採納**——它移到 §2.1 的 **V1（VALIDATION 階段）**，但**保留在 `rules.json` 中並標 `category: "validation"`**，因為 skill 在稽核既有 repo 檔案時仍然需要它。兩者不衝突：它在流程上是驗證，在稽核上是檢查項。

### 6.2 專家知識庫側欄（指示 4b）

四個固定區塊：**💡 這是什麼（大白話，不准出現術語）／📊 選錯會怎樣（具體後果）／📚 依據（論文＋連結；沒有 ✅ 依據就要寫「這是我們的判斷，目前沒有文獻支持」）／✅ 建議（給明確推薦）**。

### 6.3【v1.1 修正】第 2 步側欄文案

兩位都指出 v1.0 的文案**過度推論**。Gemini：「『專業度可能反而上升』這句話嚴重誤導，MAIN 模型僅證實機器身分在處理客觀資訊時具備無偏見優勢。」

> **💡 這是什麼**
> 你要決定這個 KOL 的可信度是**靠親身經歷**，還是**靠整理知識**。
> 「靠親身經歷」＝她說「我爬過那座山，當時風很大」。
> 「靠整理知識」＝她說「根據這三份路線報告，那座山的風險是這樣」。
> 兩種都能做出好內容，但**壞掉的方式完全不同**。
>
> **📊 選錯會怎樣**
> 這是一個 **AI 生成的角色**。當觀眾知道這件事的時候：
> - 選了「靠整理知識」→ **可以完全避開人設崩塌的風險。** 觀眾知道是 AI，也不影響「它讀完了所有資料」這件事。
>   ⚠️ 但這**不等於**專業度會自動變高——你還是要真的把資料整理對。
> - 選了「靠親身經歷」→ **這類主張會變得幾乎沒有人信。** 「我爬過那座山」對一個 AI 來說是假的，而且是一秒就能看穿的假。
>
> 而且第二種**很難救回來**。被戳破之後，這個帳號講什麼都會被打折。
>
> **📚 依據**
> Sundar (2008) 的 MAIN 模型：人會用「這是機器做的」當判斷可信度的捷徑。這個捷徑在**處理客觀資料**的任務上是優勢，在**「我親身在場」**的主張上是**反證**。
> → [MAIN Model](https://www.researchgate.net/publication/323990996)
> Lee & Eastin (2021)：揭露 AI 身分會讓具身經驗的主張更難被相信。
> → [JRIM 15(4), 822–841](https://www.emerald.com/jrim/article-abstract/15/4/822/451011/Perceived-authenticity-of-social-media-influencers)
>
> **✅ 建議**
> **選「資料庫型」。** 除非你有把握這個帳號永遠不會被問「你真的去過嗎」。
> 要做具身題材（登山、旅遊）也可以，把主張改成可查證的形式：不要說「我走過」，要說「這條路線的紀錄顯示」。
>
> ℹ️ **這五位 KOL 都還沒發布，所以現在改還來得及。** 一旦有公開內容和固定受眾期待之後，改動成本就會非常高。

### 7.1 引導式查詢

> 種子詞決定了你能看到什麼——你看到的是「跟種子詞一起出現的字」，不是「大家在講什麼」。

### 7.2【v1.1 大幅修正】跨域共現（原「結構洞候選」）

## §8 Match → 自動產生 5–10 個內容企劃（指示 4d）

### 8.1【v1.1 修正】`primaryTask` ＋ `secondaryEffects`

v1.0 寫「task 三選一，不得多選」，並宣稱三者「機制互斥」。

**GPT 的修正是對的：** 「互斥的是**創作策略的優先順序**，不是受眾行為結果。一支影片可以主打 attention、副作用帶來 comment。」

我在 v1.0 把「創作時必須選一個主目標」講成了「受眾行為互斥」，這是過度推論 Mandler 與 Rathje。

```jsonc
{
  "primaryTask": "attention",        // 必填且唯一 —— 它決定 hook 與 CTA
  "secondaryEffects": ["comment"],   // 可選，但不得反向改寫 hook 與 CTA
}
```

Gemini 堅持嚴格單一任務，理由是「宣稱能同時滿足多目標的企劃通常只是互相抵銷的平庸產物」——**這個顧慮由「`secondaryEffects` 不得改寫 hook 與 CTA」這條規則承接**，不需要靠禁止多選來達成。

### 8.2 三個硬性約束

| # | 約束 | 依據 |
|---|---|---|
| C1 | 每個企劃**必須綁定一根既有支柱** | Zuckerman 1999 ✅ |
| C2 | `primaryTask` 必填且唯一，決定 hook 與 CTA | 創作紀律（**非**受眾行為宣稱） |
| C3 | 全部通過 Zone C `block` 檢查才輸出 | 使用者指示 3 |

### 8.3【v1.1 刪除配額，改為覆蓋規則】

v1.0 的 `4/2/3/1` 被兩位共同判定為編造數字。Gemini 另指出實質後果：「會逼系統為了填滿配額，去硬拗不適合該 KOL 支柱的切角。」GPT 另抓到一個真實的不一致：**`identity` 根本不在 `task` 的 enum 裡。**

**v1.1：**
- **刪除固定比例**
- 改為覆蓋規則：**每批產出至少涵蓋 3 種 `primaryTask`，且不得全部為同一類**
- `identity` **併入 enum**，成為第四種 `primaryTask`

### 8.4 一句必須顯示的話

> 這些是**篩選過的候選**，不是預測。文獻上（Bakshy et al. 2011 ✅）預測哪一則內容會爆本身就不可靠——這個工具的價值在於**排除明顯錯的組合**，以及**逼你把理由寫下來**。

### 9.4【v1.1 新增】校準資料模型 — GPT 的阻擋條件

> 「`minRecords = 30` 被反覆用作出 B、熵權、FLOOR、倒 U 的門檻，但沒有定義每筆成效的 outcome、任務別指標、觀測窗、平台差異與成功標籤。」

**A. 依 `primaryTask` 定義的 outcome（不同任務不能用同一個成效指標）**

| `primaryTask` | 主 outcome | 次 outcome |
|---|---|---|
| `attention` | 完播率 | 3 秒留存 |
| `comment` | 每千次觀看留言數 | 留言中位長度 |
| `share` | 每千次觀看分享數 | 私訊分享（若平台提供） |
| `identity` | 每千次觀看新增追蹤 | 主頁造訪率 |

**B. 觀測窗**：主 `T+72h`、次 `T+14d`。回填時 `postAgeHours` 必須落在目標窗 ±12h，否則該筆**不納入校準**（仍保存）。

**C. 納入規則**：本專案帳號自然發布；未投放推廣；`measuredAt` 存在；`primaryTask` 已宣告。

**D. 平台**：`platform` 為必填共變項。**跨平台資料不得直接合併**——要嘛分平台建模，要嘛把平台放進模型。

**E. 校準判準（取代所有固定筆數）**

| 用途 | 判準 |
|---|---|
| `FLOOR` | `fit` 的三個帶都有資料；`experimentBand` 的成功率與 `PASS` 帶有統計上可區辨的差異 |
| 權重 | 維度間相關係數 < 0.7；各維度樣本涵蓋完整值域 |
| 倒 U（B1） | 二次項達統計顯著且對 R² 有實質增量 |

**F. 誰能標 `calibrated`**：判準達成 **且** 有人簽核並記錄判準當時的數值。**系統不得自動把任何項目標成 `calibrated`。**

## §13 已知邊界

1. PSI／關係存量測不到（→ B6）
2. `FLOOR = 30` 與 `experimentBandWidth = 10` 仍是先驗——差別是**現在有機制去檢驗它們**
3. 種子詞仍決定發現空間
4. 「對話」機制沒有單一可驗證來源
5. 中文學術原文不可達
6. **【新】等權仍是一個強假設。** 兩位都指出等權不是中性。我們接受這個批評，處理方式是：`screeningScore` 降格為分帶 + 三根維度長條並列，**讓短板看得見，而不是被平均掉**
