## §0 這份規格要解決什麼

使用者的作業流程，每週跑兩次：

1. **定義人設方向** — 例如健康型、遊戲型、政治型、運動型
2. **挑選離峰值影片主題** — 在這個方向範圍內，找出國內外相較於一般平均值特別突出、半年內異常爆紅的影片，把它們的主題列出來
3. **主題結合與推薦** — 列出 3–5（或 5–10）個主題後，依人設範圍提出「這個人設與這些主題要怎麼結合」的推薦方向

補充需求（2026-08-24）：**時事來源要分地區**。打台灣市場就查 Google 新聞與 Yahoo 新聞；香港、新加坡、日本各有各自的時事議題。這些時事同樣有熱門與離峰值的表現，要一併查詢並互相驗證。

### 0.1 這份規格與 docs/11 的關係

`docs/11` 定義的是**評分**：一個 KOL 配一個題目，過不過、幾分、為什麼。
這份規格定義的是**發現**：題目從哪裡來。

**明文約束：不新增第二套評分模型。** 掃描的產出是「題目」，題目一律回到 `matchKolToTopic` 既有的 gate → 分數 → `generatePlans` 這條路。任何在掃描階段出現的分數（離峰倍數、報導覆蓋度）**都不得進入 `screeningScore`，也不得成為 gate**。它們是選題的依據，不是配對的依據。

理由很直接：`docs/11` 花了兩輪 review 才把線性補償模型拆掉。在前面接一個新的加權公式，等於從另一頭把它裝回去。

### 0.2 §0 紀律在本規格的具體形態

| docs/11 §0 | 在這份規格裡的意思 |
|---|---|
| 1 · 只有已驗證文獻進 Zone A | 離峰值判定用的統計方法必須是**具名可查的慣例**，不是自創 |
| 2 · 不新增沒有出處的數字**或公式** | 見 §11 — 所有先驗常數集中一處、全部標 `prior`、全部寫明「這是我們定的」 |
| 3 · 影響決策的數字要能看到意義、影響度、依據 | 每一個被選出的主題都要能展開「它為什麼被選出來」的完整證據鏈 |
| 4 · 有「低到不可接受」語意的維度必須是 gate | 掃描階段**沒有任何 gate**——因為「這個題目不好」不是掃描能判定的事 |
| 5 · 禁止讓某類案例永遠無法被觀測 | 見 §3.2（成熟期造成的是**延遲**不是盲區）與 §3.6（分母必須留存）與 §5.2（2×2 四格都要顯示） |

## §1 週期、觸發與 Railway 規格

### 1.1 為什麼「每週兩次」在這個系統裡是有意義的

現行系統有一個卡住的地方：`heatConfidence` 永遠是 `none`。原因寫在 `topics/index.js`——burst 的定義是「相對於這個詞自身歷史的異常增加」（Kleinberg 2002），而系統只有一個時間切片。`scoring-config.json` 的 `timeSeries.requiredWeeklyCycles` 要求 **3 個完整週週期**（Gemini 複審：7 天的歷史會讓每一個正常的週末高峰看起來像突發）。

每週兩次的節奏，是這個系統第一次有機會合法離開 `heatConfidence: none` 的條件。門檻是先寫的（2026-08-22），節奏是後提的。

**【v1.3 · 實測】它還有第二個理由，而且是後來才量出來的。** 0-9 顯示兩次背對背、參數完全相同的查詢只有 **48%** 的貼文重疊——一次掃描是一個大池子的**一份抽樣**，不是那個池子。所以多次掃描的價值不只是累積時間序列，也是**累積覆蓋度**：每次看到不同的一半，聯集才逼近母體。這不是缺陷的補償，是這個節奏本來就該有的效果。

**但 v1.0 把它算錯了，而且錯在最不該錯的地方——用來論證這件事的那句話裡。**

v1.0 寫「每週兩次 × 3 週 = 6 次快照、21 天、3 個完整週週期」。實際跑一次固定週一／週四的排程：

| 掃描 | 距第 1 次 | `floor(spanDays / 7)` |
|---|---:|---:|
| 週一 W1 | 0 天 | 0 |
| 週四 W1 | 3 天 | 0 |
| 週一 W2 | 7 天 | 1 |
| 週四 W2 | 10 天 | 1 |
| 週一 W3 | 14 天 | 2 |
| 週四 W3 | **17 天** | **2** ← v1.0 以為這裡是 3 |
| **週一 W4** | **21 天** | **3** ← 實際上是第 7 次 |

**六次掃描只涵蓋 17 天，不是 21 天。** 兩端點都是掃描日，所以 N 次掃描涵蓋的是 N−1 個間隔，不是 N 個。

### 1.1.1 v1.1 的規則：只讀跨度，不讀次數

1. **所有成熟判斷一律只讀實際的 `spanDays` / `weeklyCycles`。** 禁止 `snapshotCount >= 6` 這類捷徑——包含文件裡的口語說法。現行 `heatConfidenceOf()` 本來就是這樣寫的（它在 2026-08-22 才剛從「看筆數」改成「看跨度」），v1.0 的文字等於把那個已修的錯誤用另一種形式寫回來。
2. **兩軌共用同一個週期跨度函式**，不各自實作。已抽出 `dashboard/server/lib/time-series.js`，`topics/index.js` 改為引用它，Track B 之後也引用同一支。
3. `/api/scan/baseline-status` 回傳 `firstCapturedAt` / `lastCapturedAt` / `spanDays` / `weeklyCycles` / `requiredWeeklyCycles`，**UI 不自行推算**。
4. 在達標之前，本規格產出的任何「升溫／變熱」語意一律禁止出現，與 `docs/11` §2.8 的用詞禁令一致（禁用：正在紅、新趨勢、爆紅、跨圈潛力、熱度上升）。

**能不能講得更確定一點？** 不能。實際跨度取決於第一次掃描落在哪一天、有沒有漏跑、cron 有沒有因為前一次還在跑而跳過。所以正確的說法是「順利的話大約三週後、第七次掃描前後」，而不是任何一個確定的次數。

### 1.2 兩軌的成熟度不同——這點必須分開講

| | Track A · 影片離峰值 | Track B · 地區時事 |
|---|---|---|
| 比較基準 | **橫斷面**：一支影片 vs. 同一頻道的其他影片 | **縱斷面**：一個議題今天的報導量 vs. 它自己前幾次掃描的量 |
| 第 1 次掃描就能用嗎 | ✅ **可以**——基準來自同一次抓取的兄弟影片 | ❌ **不行**——沒有前次可比 |
| 達到可信之前的顯示 | 正常顯示，但標明「單次橫斷面，未經時間驗證」 | 顯示絕對報導量，`spikeBaseline: none`，不得說「升溫」 |

把兩軌的成熟度混在一起講，會讓人以為第 1 次掃描就有時間序列。沒有。

### 1.3 Railway 排程

Railway 的 cron 規格（已查證 `docs.railway.com/cron-jobs`、`/guides/cron-workers-queues`）：

- cron 設在**任何一個 service** 上，執行該 service 的 start command
- 標準 5 欄位 crontab，**一律以 UTC 判讀**
- 最短間隔 5 分鐘
- **前一次還在跑，這一次就跳過**
- service 必須**執行完就結束**，不能常駐

同時，volume 的規格造成一個硬限制：**一個 volume 只掛在一個 service 上**，而且掛了 volume 的 service「同一時間只允許一個 deployment 掛載」（`docs.railway.com/deployments/healthchecks#services-with-attached-volumes`）。現行 `dashboard` service 已經掛著 volume 當 `DATA_DIR`。

**結論：掃描不能做成一個獨立的、也要寫同一個 volume 的 cron service。** 兩個 service 掛不了同一個 volume。

採用的架構：

```
┌────────────────────────────┐        ┌──────────────────────────────┐
│ scanner-cron (新 service)  │  HTTP  │ dashboard (現有 service)     │
│ · 無 volume                │───────▶│ · 掛著 volume = DATA_DIR     │
│ · cron: 0 22 * * 0,3 (UTC) │  POST  │ · 真正執行掃描、寫入快照     │
│ · 跑一支 30 行的觸發腳本   │        │ · 既有 healthcheck 不受影響  │
│ · 執行完立刻 exit          │        └──────────────────────────────┘
└────────────────────────────┘
        走 RAILWAY_PRIVATE_DOMAIN，不出公網
```

- `0 22 * * 0,3` UTC。UTC 判讀，所以日欄位要跟著往前挪一天（週日 22:00 UTC = 週一 06:00 台北）。這是 Railway cron 最容易寫錯的一格。
- 觸發用 `SCAN_TRIGGER_TOKEN` 共享密鑰，走 `RAILWAY_PRIVATE_DOMAIN` 的私有網路，端點不對公網開放。
- **手動觸發是一等公民**：畫面上要有「立刻掃描」，走同一支程式。使用者不該為了補一次掃描去改 cron。

#### 1.3.1【v1.1 修正】「兩次採樣都落在平日」對美國不成立

v1.0 用「避開週末媒體產量差異」當作挑週一／週四的理由。**這個理由只對亞洲成立。** 同一個 `0 22 * * 0,3` UTC 換算過去：

| 地區 | 第一次 | 第二次 | 是平日嗎 |
|---|---|---|---|
| TW / HK / SG | 週一 06:00 | 週四 06:00 | ✅ |
| JP | 週一 07:00 | 週四 07:00 | ✅ |
| US Eastern (EDT) | **週日 18:00** | 週三 18:00 | ❌ **第一次落在週日** |
| US Pacific (PDT) | **週日 15:00** | 週三 15:00 | ❌ 同上 |

所以 US 與以 US 為 proxy 的 GLOBAL，第一次採樣正好踩在週末——與當初挑這個時段的理由完全相反。

**v1.1 的處理：**

1. `weekday` **以該地區的當地時區計算**，不是 server 時區、也不是台北時區。快照存 `localWeekday` 與 `localCapturedAt`。
2. 排程改為 **region-aware**：亞洲區與美洲區各自一組 cron，而不是一組打全部。這比硬找一個「兩邊都是平日」的 UTC 時段乾淨——那個時段其實不存在（亞洲平日早晨 = 美洲前一天下午）。
3. 在 region-aware 排程實作之前，**US / GLOBAL 的 Track B 結果要標明採樣日落在週末**，不得與亞洲區並列比較。

#### 1.3.2【v1.1 修正】`runKey` 要含 config 版本，手動掃描不共用排程鍵

v1.0 的 `runKey = direction:region:ISO週:週內第幾次` 有兩個洞：

- 剛改完種子詞或 actor，按「立刻掃描」會拿回**舊結果**——因為 key 沒變。
- 手動掃描共用排程鍵，等於「把舊 run 打開」，不是「立刻重抓」。

```text
scheduledRunKey = ${direction}:${region}:${slot}:${configHash}
manualRunKey    = UUID
retryOf         = 可選，指向被重試的 runId
```

`configHash` 涵蓋：該方向的 seed terms、news queries、actor id 與版本、`discovery-config.json` 內容。排程仍防重複；手動是真正的一等公民，而且看得出它在重試哪一次。

### 1.4 逾時與成本的現實

`APIFY_TIMEOUT_MS` 預設 90 秒，那是給「抓一個地區的 hashtag」用的。本規格一次掃描要抓「一個方向 × 多個地區 × 多個平台 × 每個候選頻道的近期影片」，**數量級不同**。

處理方式：掃描做成**分階段、可續跑**的工作（stage-by-stage，每階段落地），不是一個 90 秒的請求。HTTP 觸發端點立刻回 `202` 與 `runId`，實際工作在背景推進，狀態由 `/api/scan/runs/:runId` 查。cron service 觸發完就結束，不等結果——這正好符合 Railway「執行完就 exit」的要求。

### 1.5【v1.1 新增】背景 Promise 不是 job system

v1.0 只寫了「每階段落地、可續跑」，**但沒有定義誰來續跑**。

這在 Railway 上是具體會發生的事，不是理論風險：redeploy、crash、OOM、service restart，detached 的背景 task 直接消失。`scanRuns` 可以留下 `stage: 'partial'`，但沒有 recovery 觸發機制的話，那就只是一筆永遠卡住的紀錄。而掛了 volume 的 service 每次重新部署本來就有一段停機（`docs.railway.com/deployments/healthchecks#services-with-attached-volumes`）——所以「部署時剛好有 run 在跑」不是例外情況，是**每次部署都會遇到**。

**v1.1 的最低要求：**

| 項目 | 規格 |
|---|---|
| **lease** | `scanRun` 記 `status` / `stage` / `leaseOwner` / `leaseUntil` / `heartbeatAt` / `retryCount` / `lastError` |
| **recovery** | process 啟動時掃一次：`status: running` 但 `leaseUntil` 已過 → 改回 `queued` |
| **併發上限** | 同時只允許明確數量的 active run；手動與 cron **不得無限堆疊** |
| **checkpoint** | 每個 stage 完成先持久化，再進下一個 stage |
| **原子寫入** | 關鍵 store 改 temp file + `rename`（**已於本次 commit 對 `store.js` 全面套用**） |

**不需要立刻上 Postgres。** `store.js` 的註解早就寫著 Postgres 是預期的升級路徑，但那是另一次改動。這裡要的只是：**不能只靠「背景 Promise 還活著」當 job system。**

## §2 人設方向層（Persona Direction）

### 2.1 為什麼需要新的一層

使用者第 1 步說的是「人設**方向**」，不是「某一位 KOL」。健康型、遊戲型、政治型、運動型是**類別**，而系統目前只有 16 位具體的 KOL。這中間缺一層。

而且缺得很具體：

- `kols/topic-axes.json` 的 domain 只有 `movie / tv / history / pop / music / news / game / sports / tech / city / book / life`。**沒有 `health`。** 健康型的題目現在會被丟進 `life` 或 `sports`。
- 現有 16 位的分布極度不均：`mia-huang` 對得上遊戲型，`vicky-lin` 對得上運動型，**政治型一位都沒有**，健康型只有半個（`ananya-kapoor` 的體式解剖）。

### 2.2 `kols/persona-directions.json`

每個方向定義：

| 欄位 | 內容 | 為什麼要有 |
|---|---|---|
| `key` / `label` | `health` / 健康型 | — |
| `domains[]` | 對應到既有 domain 的清單 | 掃描結果要能回到既有的 `classifyDomain` 體系 |
| `seedTerms{region: {tags[], keywords[]}}` | 每個地區的種子詞 | **種子詞決定了能看到什麼**——這是既有系統早就承認的限制（`seedTermsFor`），方向層讓它變成可設定而非寫死 |
| `newsQueries{region: []}` | 每個地區的新聞查詢字串 | Track B 用 |
| `pillarKeywords[]` | 方向層級的支柱關鍵字 | 供尚未綁定 KOL 時做粗篩 |
| `redlineProfile` | 這個方向特別容易命中哪幾條紅線 | 見 §8 |
| `memberKols[]` | 目前落在這個方向的 KOL id | 可以是空陣列 |
| `coverageNote` | 這個方向現在有沒有人能做 | **空的方向要講出來**，不能讓畫面看起來一切正常 |

**`memberKols` 是空的時候不擋掃描。** 掃描照跑、主題照列，但輸出明確標示「這個方向目前沒有可用人設，以下是題目盤點，不是可執行企劃」。理由：先看到題目再決定要不要做人設，本來就是合理的順序；擋下來反而逼使用者先憑空捏一個人設。

### 2.3【v1.1 修正】人設方向 ≠ scoring domain，`health` domain 從本規格移除

v1.0 順手要新增 `health` scoring domain，並自己承認「這會改變既有 16 位的比對結果」。

**Review 指出這自相矛盾，而且是對的：** 本規格開宗明義寫「這次新增發現，不改既有評分」，但新增一個 scoring domain 會改 `domain_axis_demand` → `axisDemand` → `fit`。那不是 discovery，那是一次 **scoring migration** 混在 discovery 的 commit 裡上線。

**v1.1 的分界：**

| 層 | 是什麼 | 這次動不動 |
|---|---|---|
| **人設方向**（`persona-directions.json`） | 決定「去哪裡找題目」——種子詞、新聞查詢、紅線風險輪廓 | ✅ 新增 |
| **scoring domain**（`topic-axes.json`） | 決定「這個題目吃重哪幾種能力」——進 `axisDemand`，進 `fit` | ❌ **不動** |

所以健康型是一個 discovery direction，但它找到的題目，仍然由既有的 `classifyDomain()` 落到 `life` / `sports` / `news` / `tech`。方向與 domain 是**多對多**，不是同一件事的兩個名字。

**代價，要講清楚：** 健康題落進 `life` 的 `axisDemand`，那組數字不是為健康題設計的。所以健康型方向的 `fit` 分數會比其他方向粗。這是**已知的精度損失，不是隱藏的錯誤**——回應要帶 `domainFallback: true` 與說明，讓使用者知道這一維在這個方向上比較鈍。

**要不要真的新增 `health` scoring domain？** 那要另開獨立 spec、獨立 commit、附既有 16 位的 regression 對照表（做法比照 `docs/12` §4.2）。它是一件值得做的事，但**不該搭這班車**。

## §3 Track A · 影片離峰值

### 3.1 「相對於一般平均值」——相對於哪一個平均值

這是整份規格最關鍵的一個決定。使用者說「相較於一般平均值特別突出」，而「一般平均值」有四種可能的意思，選錯會得到完全不同的清單：

| 基準 | 定義 | 它實際上會選出什麼 | 採用 |
|---|---|---|---|
| **全域平均** | 所有抓到的影片的平均觀看 | **大頻道**。一支 500 萬觀看的影片來自 800 萬訂閱的頻道，那不是離峰，那是常態 | ❌ 不採用為主判準 |
| **頻道相對** | 這支影片的觀看 ÷ **同一頻道自己近期影片的中位數** | 「這支對這個頻道來說反常地好」——排除了頻道規模與既有受眾 | ✅ **主判準** |
| **類別相對** | 相對於同 domain 的其他影片 | 有用，但不同 domain 的擴散機制本來就不同 | ✅ 次要交叉檢查 |
| **年齡匹配** | 相對於同樣發布天數的影片 | 修正「舊影片累積比較久」 | ⚠️ **V1 做不到，見 §3.2** |

**V1 採用的是「頻道相對」，不是「頻道相對 × 年齡匹配」。** v1.0 寫的是後者，但 §3.2 的實際方法只有成熟期過濾——**宣稱與內容對不上，已改**。V1 的正式名稱是**頻道相對候選（channel-relative candidate）**。

這不是新發明的方法。它和 `docs/11` 已經接受的邏輯是同一條：`heatConfidence` 之所以要求歷史快照，理由就是 Kleinberg (2002) 的「burst 是相對於這個詞自身的過去」。把「詞」換成「頻道」，同一個道理。

而且系統裡已經寫著同一個直覺，在 `apify.js` 的註解：

> Distinct accounts, not post count: a tag used 14 times by one account is that account's habit; used once each by 14 accounts, it is a trend.

一支影片相對全域很紅，可能只是那個頻道本來就大；相對它自己的兄弟影片很紅，才是這一支有什麼不一樣。

### 3.2【v1.1 重寫】成熟期過濾不等於年齡匹配

觀看數會累積。半年窗內，5 個月前的影片自然比上週的影片多。直接比會系統性地選出**舊影片**。

v1.0 的處理是成熟期過濾：未滿 `maturityDays` 的影片不算基準、也不給判定。

**Review 指出這解決不了問題，而且是對的：** 15 天的影片和 170 天的影片**都算「成熟」**，但曝光時間差 11 倍以上。把兩者一起丟進同一個頻道中位數，累積偏誤原封不動還在。成熟期過濾擋掉的只是「太新所以還沒開始累積」，不是「新舊之間累積得不一樣多」。

#### 選項與取捨

| 選項 | 做法 | 為什麼 V1 不選 |
|---|---|---|
| **A · 真做 age-matched baseline** | 只跟同頻道、發布天數相近的影片比；匹配不足回 `ageBaseline: insufficient` | 「相近」要多近？那是一個編出來的帶寬。而且半年窗內一個頻道常只有十幾支影片，切成年齡帶之後每帶剩兩三支——`minBaselineVideos` 會幾乎全數落空，等於整個功能空轉 |
| **B · `views / days` 正規化** | 換算成「每日觀看」 | **明確不選。** 這假設觀看線性累積，而實際曲線是前期陡、後期平。用一個未驗證的模型去修正另一個偏誤，是拿編的東西補編的東西 |
| **C · V1 承認做不到，改名並把偏誤攤開** | 不宣稱年齡匹配；每次掃描量測並顯示年齡偏斜 | ✅ **採用** |

#### C 的具體內容

1. **改名。** V1 的產出叫「頻道相對候選」。文件、API 欄位、UI 標籤都不得出現「已做年齡校正」的暗示。
2. **成熟期過濾保留**（它仍然擋掉「太新還沒開始累積」這個問題），但不再宣稱它處理了年齡。
3. **每次掃描回報年齡偏斜**，讓偏誤看得見而不是被說成不存在：

   > 本次入選前 10 名的發布天數中位數是 128 天，全樣本是 74 天——這批候選明顯偏舊，有一部分是累積造成的。

   欄位：`ageSkew: { selectedMedianDays, sampleMedianDays, direction }`。
4. **留下讓 A 日後成立的資料。** 每次掃描記錄同一支影片在**該次掃描時點**的觀看數（`videoObservations`）。累積數週後就有「同一支影片在第 14 / 21 / 28 天的觀看」——那才是能推出成長曲線、也才能做出**固定 post-age 觀看值**的原料。到那時 A 才有實作的基礎，而且 `maturityDays` 也才能被真的推翻而不是換一個猜的數字。

#### 延遲有多長——v1.0 這句也寫錯了

v1.0 的 `maturityDays.cost` 寫「每週兩次的節奏把延遲上限壓在 3–4 天」。**那只是掃描間隔，不是總延遲。**

正確的算法是兩段相加：

```
總延遲 = maturityDays（等它成熟，目前 14 天）
       + 最多一個掃描間隔（等下一次掃描抓到它，3–4 天）
       ≈ 至少 14 天，最多約 18 天
```

這仍然是**延遲**而不是**盲區**（§0 紀律 5 禁止的是後者：某類案例永遠不會被看到，例如被 VETO 的組合永遠不會發布、永遠不產生成效資料）。一支影片會在發布後約兩週進入可判定範圍。但兩週就是兩週，不能講成 3–4 天。

**`provisional[]` 保留**：未滿成熟期的影片仍然收錄、標 `provisional: true`，**不進主清單、不進推薦、不進統計**（Zone B 性質，`docs/11` §1.1：不得改變主候選清單的排序）。留著它的理由現在更明確了——它就是第 4 點那批軌跡資料的來源。

### 3.3 用什麼統計量——為什麼不是平均數與標準差

觀看數的分布是重尾的（少數影片吃掉絕大部分觀看）。在重尾分布上：

- **平均數**會被那一支離峰值自己拉高——你要偵測的東西污染了你的基準
- **標準差**同理，而且更嚴重

採用**對數尺度上的中位數與 MAD**：

```
logViews    = log10(max(views, 1))
median      = median(logViews of the channel's mature videos)
MAD         = median(|logViews - median|)
robustZ     = (logViews_i - median) / (1.4826 × MAD)
multiplier  = views_i / 10^median      ← 給人看的「幾倍」
```

**`1.4826` 不是我們編的。** 它是 MAD 的常態一致化常數（`1 / Φ⁻¹(0.75) ≈ 1.4826`），讓 MAD 在常態分布下與標準差同尺度，是穩健統計的標準慣例（Rousseeuw & Croux, 1993, *JASA* 88(424), 1273–1283）。這與 `scoring-config.json` 對 Cohen f² 的處理方式相同：**用具名可查的慣例，不用自創數字。**

**`MAD = 0` 的情況必須處理。** 頻道影片少、觀看數又接近時，MAD 會是 0，`robustZ` 變成除以零。此時回報 `baseline: 'degenerate'` 而不是回傳 `Infinity`——與 `topics/index.js` 既有的 `isDegenerate` / `heatDiscriminates` 同一種處理：**沒有區辨力的時候要說沒有區辨力，不要給一個看起來有信心的數字。**

### 3.4 不設倍數門檻——取 top-K，並且把分布攤開

「幾倍算離峰值？」2 倍？3 倍？10 倍？

**任何固定門檻都是編的。** 而使用者已經給了唯一不用編的數字：**3–5 個，或 5–10 個**。那是業務決定，不是對世界的宣稱。

所以：**排序取 top-K，不設門檻。** 同時回傳這次掃描的倍數分布，讓使用者看見自己的切點落在哪：

> 你選的第 5 名是 4.2 倍，落在這次掃描 312 支影片的第 97 百分位。第 6 名是 4.0 倍。

這樣做的好處是誠實的：切點是描述性的（「這批裡最突出的 5 支」），不是規律性的（「超過 3 倍就是爆款」）。系統從頭到尾沒有宣稱後者。

#### 3.4.1【v1.1】但 v1.0 一邊說沒門檻，一邊在資料模型裡偷偷需要門檻

Review 抓到的最尖銳一點，而且完全成立：

- §3.4 說「不設門檻，只排序」——那系統只做**相對排序**。
- §3.5 卻要算 `distinctChannels`＝「有幾個不同頻道**因為這個題目出現離峰**」。
- §5.2 的 2×2 更要一個二元事實：這個主題**有沒有**影片離峰。

**「有沒有離峰」是一個二元謂詞。沒有門檻，就沒有這個謂詞。** 而 top-K 永遠有前幾名——就算這批資料全部只是正常波動，第 1 名照樣長得像第 1 名。

v1.0 等於同時主張「我們沒有切點」和「我們知道誰過了切點」。這是定義層級的矛盾，不是實作細節。

#### 3.4.2 v1.1 的解法：證據是序位，切點是使用者移動的檢視參數

三條規則：

1. **底層一律連續。** `videoSamples` 存 `robustZ`、`multiplier`、以及該影片在**本次樣本**（同 region × domain）內的百分位 `percentileInScan`。**不存任何 `isOutlier` 布林值。**
2. **切點是檢視設定，不是資料性質。** UI 有一個可移動的切點，預設「本次樣本的前十分位」，**永遠與結果一起顯示**。移動它只是重新渲染，不重新掃描——因為底層是連續的。
3. **措辭跟著改。** 不說「這是離峰值」，說「**在本次 312 支樣本中排名前 4%**」。前者是對世界的宣稱，後者是對這批樣本的描述。

**這樣算不算又偷偷引進了門檻？** 不算，差別在三處，而且都可驗收：

- 它**每次掃描重新推導**（是這批樣本的百分位），不是一個跨樣本的常數；
- 它**永遠顯示在結果旁邊**，不是藏在程式裡；
- 它**可以被使用者當場移動**，而移動之後整個 2×2 會重算——所以沒有任何一格是「系統認定」的。

這與既有的 `normalize()` 在 domain 內做 min–max 是同一種地位：描述這批樣本，不宣稱一條普遍的線。

### 3.5【v1.1 修正】跨頻道重現仍是主證據，但它是序位的

一支跑得特別好的影片是 **（頻道 × 題目 × 形式 × 時機 × 封面 × 運氣）** 綁在一起的結果。把它歸因給「題目」，**在這份資料上是不可識別的**。Bakshy et al. (2011) 的發現正是：哪一則內容會爆，本身就相對不可預測——這句話已經寫在 `plans.js` 的 disclaimer 裡了。

掃描能合法宣稱的只有一件事：**同一個題目，在多個彼此無關的頻道上都排在樣本前段。**

所以主題的證據由三個**連續**量組成，不合成一個分數：

| 欄位 | 意思 |
|---|---|
| `channelsRepresented` | 這個主題在本次樣本裡總共有幾個不同頻道貢獻影片（分母） |
| `channelsAboveCut` | 其中有幾個頻道**至少有一支**落在目前切點之上（隨切點移動而變，**必與切點同時顯示**） |
| `bestPercentile` / `medianPercentile` | 這個主題的影片在樣本中的排名分布 |

排序第一鍵是 `channelsAboveCut`，第二鍵是 `medianPercentile`。單一頻道貢獻多支，計為 1。

**`channelsAboveCut` 一定要跟 `channelsRepresented` 並排顯示。** 「5 個頻道中有 4 個」和「40 個頻道中有 4 個」是完全不同的證據，只給分子會讓後者看起來像前者。

這條規則直接繼承自 `aggregatePostsToTopics` 的 `minAuthors` 邏輯（一個帳號用 14 次是習慣，14 個帳號各用 1 次才是趨勢），不是新發明。

### 3.6 分母必須留存

如果只存離峰值影片，就永遠算不出「這個題目產生離峰的機率是否高於其他題目」——因為沒有分母。這正是 §0 紀律 5 要防的事。

**每次掃描落地的是完整樣本**：每一支被評估過的影片（含大量非離峰的），連同它的 `multiplier`、`robustZ`、`baseline` 狀態、所屬頻道與題目標記。離峰清單只是這份樣本上的一個 view。

儲存量的取捨：只存統計必要欄位（id、頻道、發布時間、觀看、倍數、tags），不存全文與縮圖。與 `topicSnapshots` 只存 `{tag, domain, volume, postCount, recencyRatio48h}` 的既有做法一致。

### 3.7 資料來源的現實：目前抓不到頻道基準

**這是本規格最大的一個實作缺口，現在就要講明白。**

現行三個 Apify actor 都是 hashtag / keyword 搜尋，回傳的是**貼文**：

| 平台 | actor | 有觀看數嗎 | 能列出「某頻道的近期影片」嗎 |
|---|---|---|---|
| tiktok | `clockworks~tiktok-scraper` | ✅ `playCount` | ⚠️ actor 支援 `profiles` 輸入，但目前的 `buildInput` 只送 `hashtags` |
| instagram | `apify~instagram-hashtag-scraper` | ❌ 只有 likes/comments | ❌ 需要換 profile / reels actor |
| threads | `watcher.data~search-threads-by-keywords` | ⚠️ `view_count` 不穩定 | ❌ |

**沒有頻道近期影片列表，就沒有頻道中位數，就沒有離峰值。** §3.1 的主判準在目前的抓取設定下是跑不起來的。

所以掃描必須是**兩階段抓取**：

```
階段 1 · 發現   hashtag / keyword 搜尋 → 得到候選影片與它們的作者
階段 2 · 基準   對每一個出現過的作者，抓他的近期影片列表 → 算中位數
階段 3 · 判定   回到階段 1 的候選影片，逐支算 multiplier / robustZ
```

階段 2 是新的，它的成本是階段 1 的數倍（作者數 × 每人一次 actor run）。成本控制見 `docs/15`。

**平台建議（會影響成本與可行性，需使用者裁示）：** 離峰值分析在 **YouTube** 上最容易成立——觀看數公開、頻道影片列表可列舉、影片長度足以承載「主題」。TikTok 次之。Instagram 與 Threads 在這個用途上先天不利（沒有可靠的觀看數）。目前系統沒有接 YouTube。

### 3.7.1【v1.2 · 實測】三個平台的半年窗覆蓋能力

**Batch 0-4／0-5 已在 Railway 實跑**（`docs/reviews/2026-08-25-scan-source-probe.md`），TW 區、每平台三個 tier：

| 平台 | 半年窗 | 分頁 | 判讀 |
|---|---|---|---|
| **TikTok** | ✅ 觸及數年，180 天內佔 82.7% | ⚠️ 加大 limit 增加**密度**不增加**觸及** | 可做 Track A |
| **Instagram** | ❌ 實際只有 **~25 天** | ❌ 加大 limit 只是拿到更多當月貼文 | 不可做 Track A |
| **Threads** | ❌ 時間戳全部解析失敗（見 §3.7.2） | — | 不可做 Track A |

**所以「半年內離峰值掃描」這個名字站得住——但只在 TikTok 上。** 這與上一段基於觀看數的判斷**獨立地指向同一個結論**：三個平台裡只有 TikTok 能同時提供半年窗與可靠的觀看數。兩個不同的理由，同一個答案。

**兩個影響設計的實測細節：**

1. **要更舊的內容只能換種子詞，不能加大 limit。** TikTok 的 tier 100 與 tier 300 回傳的最舊貼文**完全相同**——actor 可及的池子有一個固定的底，tier 100 就摸到了。這讓 §8.2 的「種子詞邊界」偏誤比原本寫的更強：**它不只決定看到什麼題材，也決定看得回多久。**
2. **`resultsPerPage` 是每個 hashtag 各自的數量，不是總數。** 三個種子 tag → 實際回傳是 ×3。成本估算要用這個乘數。

### 3.7.3【v1.3 · 實測】profile actor 通過——主判準成立

`docs/15` §2.2 的三個備案（接 YouTube／換 actor／退成類別相對）**都不需要動用**。

`clockworks~tiktok-scraper` 的 `profiles` 輸入實測（TW 區、照 actor 順序取前 5 個作者、每個要 30 篇）：

| rank | posts | viewsCoverage | medianViews | spanDays |
|---:|---:|---:|---:|---:|
| 1 | 30 | 1.0 | 1,577 | 231.9 |
| 2 | 30 | 1.0 | 30,800 | 70.1 |
| 3 | 30 | 1.0 | 156 | 61.1 |
| 4 | 23 | 1.0 | 8,549 | 173.0 |
| 5 | 30 | 1.0 | 7,141 | 297.0 |

五個全部 `staysOnProfile: true`、`viewsCoverage: 1.0`、篇數高於 `minBaselineVideos = 8`。**頻道中位數算得出來。**

而且 `medianViews` 橫跨 **156 到 30,800**——這正好證明 §3.1 選頻道相對是對的。用全域平均比，中位 156 的那個帳號每一支影片都會被判成失敗，中位 30,800 的每一支都會被判成成功。那量到的是頻道規模，不是題目。

#### 基準是「最近 N 篇」，不是「最近 180 天」

同樣要 30 篇，發文頻繁的帳號只覆蓋 61 天，稀疏的覆蓋 297 天。

**所以 `baselineLookbackDays = 180` 描述的不是實際發生的事**，實際發生的是「這個頻道最近 30 篇」。

這反而更適合頻道相對中位數——它是該頻道近期行為的固定 N 抽樣，不受發文頻率影響。但**常數要改口徑**：從「回看幾天」改成「回看幾篇」（`baselineRecentPosts`），否則文件說的和程式做的又對不上，那正是 `growth7d` 其實是 48 小時的那一類錯。

### 3.7.2【v1.2 · 實測】Threads 的時間戳從來沒有被解析成功過

探測發現的既有生產環境 bug：`watcher.data~search-threads-by-keywords` 的 `created_at` 是 **Unix epoch 整數（秒）**，不是 ISO 字串。`Date.parse(1787631594)` 會把數字轉成字串 `"1787631594"`，那不是合法日期 → NaN。

**後果：這個連接器上線以來，每一則 Threads 貼文都被當成沒有時間戳**，`recencyRatio48h` 對任何由 Threads 帶進來的標籤一律算成「沒有一則是最近的」。

它不噴錯、不讓測試變紅——缺失的日期靜靜地變成一個 0。**探測抓到它，只因為量測工具把 `undated` 當成一個獨立的數字回報**，而不是讓它消失在 0 裡面。

已修：新增 `toIso()`，三個平台走同一支正規化。

## §3A【v1.1 新增】主題身分（Canonical Topic Identity）

### 3A.1 沒有這一層，前面幾節的數字全部可能是字串分組的幻覺

整份設計反覆依賴「**同一個**主題」：

- Track A：同一題在多個頻道出現 → `channelsRepresented` / `channelsAboveCut`
- Track B：同一議題今天的覆蓋度 vs. **它自己**的歷史
- 交叉驗證：影片的題和新聞的題**是不是同一件事**

v1.0 只定義了最後一項（§5.3 兩軌怎麼對上），**完全沒有定義前兩項**。Track A 內部怎麼把不同影片歸成同一題？Track B 跨週怎麼認出這是上週那個議題？

Review 舉的例子正中要害：

> 「Ozempic 減重副作用」／「GLP-1 減肥藥風險」／「瘦瘦針副作用」

這三個可能是同一題，也可能不是。**只靠 hashtag 會碎成三題**（於是 `channelsAboveCut` 永遠是 1，跨頻道重現這個主證據直接失效）；**只靠種子詞又會把整個「健康」黏成一題**（於是什麼都是同一題，同樣沒有資訊）。

而 Track B 的縱斷面比較更嚴重：如果這一週的議題 ID 和上一週對不起來，那所謂「相對於它自己的歷史」就沒有「它自己」——整個 §4.3 建立在一個不存在的東西上。

### 3A.2 資料契約

```text
canonicalTopicId      穩定 ID，跨掃描不變
displayTitle          給人看的標題
region                身分在地區內成立，不跨地區合併（理由同 §6.1）
language
aliases[]             所有被歸到這個 ID 的表面字串
entities[]            命名實體：人、地、機構、產品、藥名
sourceTerms[]         把它帶出來的種子詞／新聞查詢
firstSeenAt / lastSeenAt
mergeHistory[]        什麼時候把哪兩個 ID 併起來、誰決定的
splitHistory[]        什麼時候拆開、為什麼
identityMethod        'exact' | 'alias' | 'entity' | 'manual'
identityConfidence    或 needsReview: true
```

### 3A.3 V1 用決定性規則，不用 embedding

**V1 不做 embedding 或 LLM clustering。** 理由與這個 repo 一貫的立場一致：相似度模型會產生一個看起來精確、實際上沒有校準資料可以檢驗的分數，而且它的判斷不可重播。

V1 的規則，依序：

1. **正規化字串完全相同** → 同一題（`identityMethod: 'exact'`）
2. **命中已登記的 alias** → 同一題（`'alias'`）
3. **命名實體集合有交集，且在同一 region** → 標為**候選合併**，`needsReview: true`，**不自動合併**
4. **其餘** → 各自獨立

第 3 條刻意不自動合併：實體交集會把「Ozempic 減重」和「Ozempic 缺貨」誤併成一題。**候選合併進人工佇列**，人決定之後寫入 `aliases[]` 與 `mergeHistory[]`——所以下一次掃描就會自動走第 2 條。這條路徑是可重播、可審查的，而且會**隨著使用累積變準**。

### 3A.4 必須是可重播的

`mergeHistory` / `splitHistory` 不是稽核裝飾品。Track B 的縱斷面比較會回頭讀歷史快照，如果主題身分曾經被合併過，**歷史數列的意義就變了**（兩條線變一條）。沒有 merge 紀錄，就無法解釋「為什麼上週的覆蓋度突然翻倍」——那可能只是合併造成的，不是真的有事發生。

所以：**任何一次 merge/split 都要能重建合併前的數列。**

## §4 Track B · 地區時事議題

### 4.1 來源

依使用者指示，時事分地區查詢：

| 地區 | 主來源 | 備註 |
|---|---|---|
| **TW** | Google News（`hl=zh-TW&gl=TW&ceid=TW:zh-Hant`）＋ Yahoo 奇摩新聞 | 使用者指定 |
| **HK** | Google News（`hl=zh-HK&gl=HK&ceid=HK:zh-Hant`）＋ Yahoo 香港 | 中文用詞與台灣不同，查詢字串要各自寫 |
| **SG** | Google News（`hl=en-SG&gl=SG&ceid=SG:en`） | 英文為主 |
| **JP** | Google News（`hl=ja&gl=JP&ceid=JP:ja`）＋ Yahoo!ニュース | |
| **KR / US / MY / CN / GLOBAL** | Google News 對應語系 | CN 的可及性另議 |

**【v1.3 · 已實測】** 七區的 Google News RSS 全部回 200、全部是合法 XML、單次 30–38 則，同一 feed 連打 5 次全部 200（短期無速率限制，不宣稱長期）。**免 key、免費確認成立。**

#### 4.1.1【v1.3】走 `rss/search`，不走主題 feed

實測差距是三十倍：

| feed | 則數 | 觸及 | 媒體家數 |
|---|---:|---:|---:|
| TW 主題 feed `/rss?hl=…` | 34 | **0.7 天** | 19 |
| TW search feed `/rss/search?q=健康` | 102 | **30.4 天** | 51 |

主題 feed 是「今天的頭條」，撐不起 `newsWindowDays = 7` 的視窗，更撐不起縱斷面基準。

**→ Track B 走 `rss/search` ＋ `persona-directions.json` 的 `newsQueries`。** 這讓 `newsQueries` 從「設定資料」升格為**必要輸入**——沒有它就沒有 Track B。30 天的觸及對 7 天視窗綽綽有餘。

#### 4.1.2【v1.3】`outletCount` 必須從 `<source url>` 取

七區的「從 `<link>` 數出的媒體家數」**全部是 1**——Google 的 `<link>` 是 `news.google.com` 轉址。真正的媒體在 `<source url="…">`，那裡是 16–51 家。

所以 §4.4-3 的「以媒體網域去重」不是建議而是必要：**只看 `<link>`，每一區的媒體覆蓋度都會是 1。**

#### 4.1.3【v1.3】Yahoo 是一家媒體，不是聚合來源

| region | path | status | 則數 |
|---|---|---:|---:|
| TW | `tw.news.yahoo.com/rss/` | 200 | 100 |
| TW | `tw.news.yahoo.com/rss/health` | 200 | 30 |
| HK | `hk.news.yahoo.com/rss/` | 200 | 100 |
| SG | `sg.news.yahoo.com/rss/` | 200 | **5** |
| JP | `news.yahoo.co.jp/rss/topics/top-picks.xml` | 200 | **8** |
| US | `www.yahoo.com/news/rss` | **403** | — |

**所有 Yahoo feed 的 `<source url>` 家數都是 0**，連結全落在 Yahoo 自己的網域。

**→ Yahoo 不能貢獻媒體多樣性。** 100 則 Yahoo 文章是 1 家媒體，不是 100 家；併進 `outletCount` 會虛報覆蓋度。它的價值是另一種東西——**「Yahoo 自己選了什麼」是獨立於 Google 的編輯訊號**，兩者分開計、不相加。

**Yahoo 軌只在 TW／HK 成立**（SG／JP 太薄、US 403）。

> ✅ **【v1.3】已在 Railway 實機驗證**，見 `docs/reviews/2026-08-25-scan-source-probe-part2.md`。開發環境的 proxy 擋掉這兩個網域，所以探測跑在容器裡、結果走 Railway log 出來。

### 4.2 覆蓋度不是需求——這是本軌最容易犯的錯

新聞沒有觀看數。Google News 的排序是編輯與演算法的選擇，不是受眾投票。所以 Track B 能得到的量化訊號只有：

- `outletCount` — 有幾家不同媒體報導
- `articleCount` — 這個議題累積幾篇
- `daysCovered` — 連續被報導幾天

這三個都是**媒體供給**的量測，**不是閱聽需求**的量測。

把它叫「熱度」，就是重蹈系統早就修正過的錯誤：`volume` 在 Apify 路徑上其實是「樣本共現次數」，硬叫它「量體」就是在編造精確度——所以現在有 `volumeMeaning: 'sample_frequency'` 這個欄位。

**Track B 的欄位一律命名為 `coverage*`，UI 標籤一律是「報導覆蓋度」，禁止出現「熱度」「熱門度」。** 需要對應的 `coverageMeaning: 'media_supply'` 欄位。

### 4.3 時事的離峰值

議題的「離峰」= 它的報導覆蓋度相對於**它自己過去**的異常增加。這是縱斷面的，需要 `canonicalTopicId` 才成立（§3A.1）。所以：

- **未達 `requiredWeeklyCycles` 個完整週週期前：** `spikeBaseline: 'none'`，只顯示絕對覆蓋度，禁止任何升溫語意
- **達標後：** 可計算，但仍受人工批准閘門管制

**【v1.1 修正】批准旗標不共用。** v1.0 寫「與 `heatConfidence` 同一套規則」，Review 指出**週期門檻可以共用，人工批准不行**——這是對的：

> 批准「hashtag 樣本共現密度的歷史可以離開實驗區」，不等於批准「新聞覆蓋度基準也已經可靠」。兩者的資料源、偏誤、窗長都不同。

所以拆成兩個旗標，各自簽核（現已落在 `kols/discovery-config.json`）：

```text
timeSeries.topicHeat.approved       ← 既有的 hashtag 樣本共現密度
timeSeries.newsCoverage.approved    ← 新增的新聞覆蓋度
```

`requiredWeeklyCycles` 則**只留一份 source of truth**，兩邊引用同一個值、共用 §1.1.1 抽出的同一支跨度函式，不各自複製。

沿用既有的 `W-NO-BASELINE`（沒有歷史基準就談時機）警示規則——這條紅線 v1.1 就寫好了，正好對上。

### 4.4【v1.1 重寫】新聞的四個結構性偏誤

1. **媒體週期偏誤——而且 v1.0 的解法對美國不成立。** 週一到週五的新聞產量遠高於週末。v1.0 說「固定週一與週四採樣，避開週末」——但 `0 22 * * 0,3` UTC 在美東是**週日 18:00** 與週三 18:00（§1.3.1 有完整換算表）。第一次採樣正好踩在週末，與挑這個時段的理由完全相反。
   **處理：** `weekday` 一律**以該地區當地時區**計算並存進快照（`localWeekday` / `localCapturedAt`）；排程改 region-aware。在那之前，US / GLOBAL 的結果要標明採樣日落在週末。
2. **【v1.1 新增】7 天視窗每週掃兩次會高度重疊。** `newsWindowDays = 7`、掃描間隔 3–4 天 → 相鄰兩次的視窗重疊 3–4 天。**今天看到的「上升」很可能只是上一個視窗的同一批文章還在裡面**，這是強自相關，不是新事件。
   **處理：不存聚合值，存 article-level 原始資料**：`publishedAt` / `outletDomain` / `canonicalTopicId` / `title`。日聚合在讀取時計算，視窗長度是查詢參數而不是寫死在資料裡。這樣一來 `newsWindowDays` 不再是一個會污染歷史資料的常數，而是一個隨時可以改、可以並排比較的檢視設定——也就是說，這條偏誤變成**可量測**而不只是被記下來。
3. **同一則事件的重複計算**：Google News 會把同一事件的多家報導聚成 cluster，但聚類不完美。`outletCount` 要以**媒體網域去重**，不是以文章數。與 `aggregatePostsToTopics` 用 distinct authors 而非 post count 是同一個道理。
4. **議題身分跨週要對得上**，否則「相對於它自己的歷史」沒有「它自己」。見 §3A。

## §5 兩軌交叉驗證

### 5.1 使用者要的「查詢和驗證」是什麼

新聞熱議 ≠ 短影音會紅。反過來也成立。這兩件事只有部分重疊，而**重疊的那一格特別值得看**。

### 5.2【v1.1 重寫】2×2 是檢視切面，不是資料的性質

v1.0 的 2×2 直接用「有／無影片離峰」當軸——而 §3.4.1 已經確認那個謂詞不存在。所以 2×2 的定義也要跟著改。

**兩軸都是使用者可移動的切點，而且永遠與矩陣一起顯示：**

- 橫軸：影片證據 ≥ 切點（預設「本次樣本前十分位」）
- 縱軸：新聞覆蓋度 ≥ 切點（預設同上，在該地區該次抓取的樣本內）

|  | **影片證據在切點之上** | **在切點之下** |
|---|---|---|
| **新聞覆蓋在切點之上** | **① 雙軌命中**<br>兩個獨立來源指向同一件事。最強的候選。 | **③ 只有議題**<br>媒體在報，短影音沒動靜。對 AI 人設風險最高——多半是政治／突發，且無現成的影片語法可循。 |
| **在切點之下** | **② 只有影片**<br>平台原生題材（形式、梗、挑戰）。生活風格型人設最常見的好題。 | **④ 兩者皆在切點之下**<br>不入選，**但必須留存**——它是①②③的分母。 |

**三條驗收規則：**

1. **四格都要在畫面上出現。** 只顯示①，會讓②③永遠不被觀察到，那就是 §0 紀律 5 禁止的事。而且②在實務上很可能是最有用的一格——`docs/12` 匯入的 11 位人設幾乎全是生活風格型，她們的好題大多不會出現在新聞裡。
2. **矩陣上方永遠印著當下的兩個切點，以及移動它們的控制項。** 使用者移動切點，格子重算，不重新掃描。
3. **每一格顯示的是「N 個主題 / 全部 M 個」**，不只顯示 N。

**措辭：** 格子的標題是「影片證據在切點之上」，不是「有離峰值」。系統從頭到尾不宣稱哪個主題「是」離峰值。

### 5.3 兩軌之間怎麼對上

不做語意相似度模型（那是另一個沒有校準資料的黑盒）。用可解釋的規則，且**在 `canonicalTopicId` 已經成立之後才做**（§3A）：

1. **關鍵字重疊**：沿用既有的 `containsKeyword`（`text.js`），跨語言比對用 `pillar_keywords` 已經在做的那套
2. **命名實體重合**：人名、地名、機構名、產品名
3. **時間鄰近**：見下方定義

三條各自輸出「有／無」與命中的具體字詞，**不合成一個分數**。合成分數又會需要權重，權重又要編。

#### 5.3.1【v1.1 補上】「時間鄰近」的時間基準是什麼

v1.0 只寫「影片離峰的發生時間 vs. 報導覆蓋度上升的時間」，但兩邊都沒有定義是哪一個時間。這裡定死：

| 一邊 | 用哪個時間 | 為什麼不用別的 |
|---|---|---|
| 影片側 | **影片的 `publishedAt`** | 不用 `scanTime`——那是我們什麼時候去看，與事件無關；也不用「觀看數起飛的時點」，因為我們沒有逐日觀看數（正是 §3.2 第 4 點要補的那批資料） |
| 新聞側 | **該議題文章的 `publishedAt` 中位數** | 不用 `firstSeenAt`（受我們第一次掃描的時間污染），也不用覆蓋度峰值日（達標前根本算不出峰值） |

**限制要一起寫出來：** 影片側用發布時間，等於假設「影片發布 ≈ 話題發生」。對追時事的影片大致成立，對長尾常青題完全不成立。所以**時間鄰近這一條對常青題不適用**，回傳 `timeProximity: 'n/a'` 而不是 `false`——「不適用」和「不鄰近」是兩回事。

## §6 國內外，與「能不能搬過來」

### 6.1 不同地區的離峰值不放在同一張排行榜

理由與 `docs/11` §2.9 完全相同：熱度在 domain 內正規化，因為不同題材的擴散機制不同（Romero, Meeder & Kleinberg 2011）。地區之間差得更多——語言、平台佔比、文化指涉、媒體生態。

**正規化在 `(region × domain)` 內進行。** 回應帶 `crossRegionComparable: false`，與既有的 `crossDomainComparable: false` 並列。

### 6.2 可移植性是分類，不是分數

國外的離峰題目要不要搬回台灣，取決於它紅的**機制**：

| 類別 | 判定依據 | 可移植性 |
|---|---|---|
| **通用機制** | 它紅是因為形式／結構（前後對比、拆解、挑戰、反差） | 高——換掉在地素材即可 |
| **在地變體** | 需求是普世的（想變健康、想省錢），但表達方式在地 | 中——需要重寫，不是翻譯 |
| **在地指涉** | 依賴一個具名的在地人物、事件、政策、迷因 | 低——搬過來多半失效 |

**這三類是有定義的質性分類，不給數字。** 判定交給語意層，依 `docs/11` §5.4 的兩層規則：規則層給候選，語意層做判定，判定要記進 `judgementLog` 以便日後檢驗判得準不準。

## §7 主題 → 人設結合建議

### 7.1 分兩層，因為「方向」和「KOL」不是同一件事

**方向層（沒有綁定 KOL 時）：**
輸出的是 **結合簡報（combination brief）**，不是分數。內容：這個題目在這個方向裡可以站在什麼位置、它為什麼在別的頻道上成立、搬過來要換掉什麼、可能踩到哪些紅線。
**明確標示 `scored: false`。** 沒有 KOL 就沒有 `fit`、`pillar`、`homophily`、`credibilityMode`——四個維度有三個是 gate 或分數，全部需要人設資料。硬給一個分數就是編。

**KOL 層（方向裡有 KOL 時）：**
每個入選主題經 `makeAdHocTopic()` 轉成 topic 物件，走 `matchKolToTopic()` → `generatePlans()`。**完全沿用既有引擎，不改評分。**

### 7.2 掃描帶來的證據要接上既有的維度備註

既有的 `notes.js` 讓每個分數都能展開意義／影響度／依據。掃描產出的主題多了一段既有 fixture 題目沒有的東西：**真實的來源證據**（哪幾支影片、幾個頻道、排在樣本第幾百分位、哪些媒體報了、報了幾天）。

這段證據掛在主題上（`topic.discoveryEvidence`），不掛在維度上——它解釋的是「這個題目為什麼被端出來」，不是「這個 KOL 為什麼適合它」。兩件事混在一起，會讓人以為排名高等於契合高。**不等於。**

### 7A【v1.1 新增】scan-topic adapter 契約——不然「不污染評分」只存在文件裡

Review 查了實際程式，發現 §7.1 那條路走不通，而且**現行系統當下就在犯這個錯**：

```js
// dashboard/server/lib/topics/index.js — makeAdHocTopic()
heat: input.heat ?? 50,
```

`makeAdHocTopic()` 只挑固定欄位重建物件，所以：

1. **`discoveryEvidence` 會被整段丟掉** — §7.2 描述的證據鏈在進引擎的那一步就斷了。
2. **`heat` 會憑空變成 50。** 一個完全沒有樣本共現資料的掃描題，進 `matchKolToTopic()` 之後，`buildTiming()` 會顯示一個 **50 分的「樣本共現密度」**。那個 50 不是量測結果，是預設值——而它會被畫成一個看起來有意義的數字。

這正好違反本規格從頭到尾在講的那件事：**不要把不同來源的證據混成同一種數字。** 說「掃描不污染評分」，但資料一進既有引擎就已經被污染了。

#### 契約

```text
source            'scan'（既有值：'region' | 'hook' | 'manual'）
canonicalTopicId  §3A
region / language
discoveryEvidence 完整帶過去，不裁切
heat              null —— 沒有樣本共現資料就是 null，不是 50
heatConfidence    'none'
timingCaveat      「這個題目來自離峰值掃描，沒有樣本共現密度資料。旁邊的時機欄位不適用。」
```

#### 已修的部分

`match.js:419` 本來就寫 `Number.isFinite(topic.heat) ? round(topic.heat) : null`——**它早就準備好接 null 了**，只是上游從來不給 null。所以修的是上游：

- `makeAdHocTopic()` 的 `heat` 不再預設 50；沒有傳就是 `null`。
- **`hookToTopic()` 有同一個缺陷**（`match.js:444` 的 `heat = 50` 預設），一併修掉。KOL 自己宣告的常青題目同樣沒有任何平台樣本，顯示 50 是同一種憑空。
- 兩者都改為透傳 `discoveryEvidence` 與 `source`。

**不改 `gates.js` / `match.js` / `notes.js` 的評分公式**——`heat` 本來就不進 `screeningScore`（`match.js:357` 的註解寫著 `heat excluded`）。這次改的只有「顯示層拿到什麼值」。

### 7.3 主題清單的組成必須跨 domain，且原始排名要同時看得到

離峰值有一個可預測的偏誤：**衝突性、道德情緒強的題材系統性地跑得更遠**。Brady et al. (2017) 已在本 repo 引用過——道德情緒語言提升擴散，但受群體邊界限制。

後果很具體：**一個健康型人設的掃描結果，很可能被政治題掃光**，因為那些影片的倍數就是比較高。

處理方式（是選取規則，不是評分公式）：

- K 個名額先**每個有候選的 domain 保底 1 名**，剩餘名額依排名分配
- **同時完整顯示未經分層的原始排名**

第二條是關鍵：分層只改變「建議先看哪些」，不隱藏任何東西。使用者永遠看得到「如果純按排名排，前 10 名是這些」。

#### 7.3.1【v1.1 補上】domain 數量大於 K 的時候怎麼辦

v1.0 說「每個 domain 保底 1 名」，但沒處理**有候選的 domain 比 K 還多**的情況——那時「每個保底 1」在數學上不可能成立。使用者選 K=3、掃出 7 個 domain 各有候選，就直接矛盾。

規則（純粹是名額分配，不宣稱任何東西）：

1. **domain 依「該 domain 最佳主題的排名」排序**
2. 由前往後，**每個 domain 各拿 1 名**，直到 K 用完
3. K 用完時，剩下的 domain **不是被丟掉**——它們列在「本次還有 4 個題材類別有候選，但超出你要的 K 個名額」，可以一鍵展開
4. 反之，domain 數少於 K 時，剩餘名額依整體排名分配

第 3 點是重點：**超出名額不等於不存在。** 靜默丟掉會讓使用者以為只有這幾類有東西——那正是 §0 紀律 5 禁止的事。

## §8 紅線與偏誤

### 8.1 政治型方向要特別處理

使用者把政治型列為人設方向之一。對一個 AI 人設，政治內容命中既有規則的機率明顯高於其他方向：

| 既有規則 | 為什麼政治題特別容易命中 |
|---|---|
| `R-REAL-PERSON-IMPERSONATION` | 政治題大量涉及具名真實人物 |
| `R-HATE-HARASSMENT` | 立場性內容容易滑向貶低特定群體 |
| `R-FAKE-CERTAINTY` | 政治判斷被講成確定事實 |
| `W-OUTGROUP` | 以外團體對立換互動——政治題的預設互動機制 |
| `R-EMBODIMENT` | 「我在現場」「我認識的人說」對 AI 人設不成立 |

再加上 §7.3 的選取偏誤：離峰值機制本身就會多選政治題。

**建議新增 `W-POLITICAL-OUTLIER`（warn，不是 block）。**

依 `docs/11` §5 對紅線分級的四項客觀判準（不用「模型投票」）：

1. **可否被關鍵字可靠識別？** 否——所以是 warn，且必須進語意層
2. **誤擋的代價？** 高。政治評論是正當內容，block 會是產品決策不是安全決策
3. **漏放的代價？** 高但不是不可逆——它會連帶命中上表那些既有 block 規則
4. **是否為本設計自身引入的偏誤？** **是**——這是關鍵。倍數排序偏好衝突題材，是掃描機制造成的，不是題材本身的問題。所以警示的正確內容不是「政治題不好」，而是「這個題目排前面，有一部分是排序方式造成的」。

第 4 點也決定了措辭：警示要指向**方法**，不是指向**題材**。

### 8.2 這份設計已知會有、但無法在資料內消除的偏誤

| 偏誤 | 後果 | 處理 |
|---|---|---|
| **種子詞邊界【v1.2 加強】** | 只看得到種子詞帶得出來的東西，**而且只看得回種子詞能翻到的那麼久**——實測確認加大 limit 不會讓觸及變深（§3.7.1） | 每次快照記錄完整種子詞與新聞查詢（沿用 `seedTermsFor` 既有做法） |
| **成功者偏誤** | 只看紅的影片，無法知道同題目失敗了幾次 | §3.6 分母留存 |
| **歸因不可識別** | 影片紅不等於題目好 | §3.5 跨頻道重現為主判準；沿用 `plans.js` 的 disclaimer 措辭 |
| **平台偏誤【v1.2 實測】** | **三個平台裡只有 TikTok 能做 Track A**：IG 實際只覆蓋 ~25 天、Threads 時間戳原本全部解析失敗 | §3.7.1 實測結果；`docs/15` 提出裁示點 |
| **媒體供給偏誤** | 報導多 ≠ 有人想看 | §4.2 全部改名為 `coverage*` |
| **語言偏誤** | 中文與英文查詢得到的世界不同 | 各地區各自寫查詢，不做機器翻譯 |
| **年齡偏誤【v1.1】** | 半年窗內舊影片累積比較久，會系統性排前面 | §3.2 承認未解決、改名、並每次量測 `ageSkew` 顯示偏斜方向 |
| **候選作者截斷偏誤【v1.1】** | 見下方 8.2.1 | 完整作者帳目 + 被截斷者的分布摘要 |
| **視窗重疊【v1.1】** | 每週兩次 × 7 天窗 → 相鄰兩次重疊 3–4 天，強自相關 | §4.4-2 改存 article-level，視窗變成讀取時參數 |
| **單次抽樣不穩定【v1.3 · 實測】** | 兩次背對背、參數完全相同的查詢只有 **48%** 的貼文重疊。跨週的差異有相當一部分是抽樣，不是世界變了 | 見 §8.2.2 |

#### 8.2.2【v1.3 新增】一次掃描是一份抽樣，不是母體

0-9 實測：兩次相隔幾十秒、參數完全相同的 discovery，貼文 `recallOfA 0.476`、作者 `0.487`。**兩次之間世界沒有變，變的是抽樣。**

三個後果，都必須寫進產品行為而不只是文件：

1. **跨週比較要非常保守。** 某個主題這週有、上週沒有，在 48% 的重疊率下經常會發生。**單憑「上週沒看到」不能說它是新的**——這正是 §4.3 的 `spikeBaseline` 在達標前必須是 `none` 的另一個理由。
2. **單次掃描內的跨頻道重現（`channelsAboveCut / channelsRepresented`）比跨週比較可靠。** 它在同一份抽樣內比較，不受兩次抽樣差異影響。這強化了 §3.5 已經選定的主判準——現在有實測支持，不只是推理。
3. **每週兩次的第二個理由**：覆蓋度累積，見 §1.1。

另外：單次 300 筆裡有 27 筆重複 id。**去重是必要的**，不是防禦性寫法。

### 8.2.1【v1.1 新增】只記「有幾個沒抓」還不夠

為了控成本，只對「進入候選」的作者抓頻道基準，超過 `maxChannelFetches` 就截斷（§8 成本控制）。

**問題是：誰先進候選，是由 hashtag actor 自己的排序決定的。** 基準只會覆蓋 actor 挑過一輪的那群帳號。

**【v1.3 · 實測，比預期輕】** 0-7 量了前 20 名的 `medianViewsInSample` 對 `upstreamRank`：rank 4 是 120 萬、rank 8 是 20、rank 13 是 19、rank 17 是 24 萬——**沒有任何單調趨勢，不是 popularity 排序**。所以取前 N 個作者不會系統性地取到最大的那些。

**帳目仍然要記。** 「這一次不是 popularity 排序」不等於「永遠不是」——actor 換版本就可能變，而那時沒有帳目就看不出來。

v1.0 只要求記「有 37 個作者因上限沒抓」。**那個數字說不出被漏掉的是什麼類型**——漏掉 37 個小帳號和漏掉 37 個大帳號，對基準的意義完全不同。

必須記：

```text
authorsDiscovered          這次總共發現幾個作者
authorsEligibleForBaseline 其中幾個符合抓基準的條件
authorsFetched             實際抓了幾個
authorsSkippedByCap        因上限跳過幾個
selectionOrder / upstreamRank  是依什麼順序挑的、上游給的名次
skippedProfile             被跳過那群的 region / domain / 初始訊號分布摘要
```

UI 的涵蓋範圍要能說：**「本次發現 420 位作者，只對前 100 位建立了頻道基準」**——而不是只顯示 100 位，看起來像完整母體。

## §9 資料模型

### 9.1 新增的 store（`lib/store.js` 的 `FILES`）

| key | 檔案 | 一列是什麼 | 為什麼要留 |
|---|---|---|---|
| `scanRuns` | `scan-runs.json` | 一次掃描（方向、地區、時間、種子詞、查詢、階段狀態、耗時、成本） | 冪等性與可重跑；同時是「這次看到的世界有多大」的紀錄 |

| `channelBaselines` | `channel-baselines.json` | 一個頻道在某次掃描的中位數／MAD／樣本數 | 避免重複抓取；也讓「基準本身是否漂移」可被檢驗 |
| `newsArticles`【v1.1 改】 | `news-articles/<runId>.json` | **一篇文章一列**：`publishedAt` / `outletDomain` / `canonicalTopicId` / `title` | §4.4-2：存聚合值會把 `newsWindowDays` 這個常數烤進歷史資料；存 article-level 才能事後改視窗、才能量測重疊造成的自相關 |
| `canonicalTopics`【v1.1 新】 | `canonical-topics.json` | 一個主題身分（§3A.2 的完整契約，含 alias 與 merge/split 紀錄） | 沒有它，跨頻道重現與跨週基準都只是字串分組 |
| `videoObservations`【v1.1 新】 | `video-observations/<runId>.json` | 同一支影片在**這次掃描時點**的觀看數 | §3.2 第 4 點：累積後才有成長曲線，`maturityDays` 與 age matching 才有被推翻的可能 |
| `scanTopics` | `scan-topics.json` | 掃描選出的主題，含證據鏈與**連續的**排名／百分位 | 供後續回頭比對「當時選它的理由，事後看對不對」 |

**不存 `isOutlier` 布林值**（§3.4.2）。切點是檢視參數，存進資料就變成資料的性質了。

沿用既有 store 的 append-only、檔案落地、掛在 `DATA_DIR` volume 的做法。**不引入資料庫**——`store.js` 的註解已經寫明 Postgres 是預期的升級路徑，但那是另一次改動，不混在這次。

### 9.2 保留期限要現在就想

`videoSamples` 是這裡面成長最快的。每次掃描數百列、每週兩次，一年約數萬列的 JSON 檔——`store.js` 是整檔讀寫的，會變慢。

規格：**`videoSamples` / `newsArticles` / `videoObservations` 依 `runId` 分檔**，索引留在主檔。這是唯一需要偏離既有 store 形態的地方，理由是量級，不是偏好。

### 9.3【v1.1 新增】兩件跨模組的一致性要求

1. **週期跨度只有一份實作。** `dashboard/server/lib/time-series.js` 是唯一的來源，`topics/index.js` 已改為引用它，Track B 之後也引用同一支。§1.1.1 的錯誤之所以會發生，就是因為文件裡的算術和程式裡的算術是分開維護的。
2. **原子寫入。** `store.js` 的 `writeAll()` **已改為 temp file + `rename`**。原本是裸 `fs.writeFileSync`——process 在寫到一半被中斷（Railway redeploy 時的正常停機就會），整個 store 檔會被截斷。這在加入掃描的大量狀態更新之後只會更常發生，但它**現在就已經是風險**，不是掃描才引進的。

| `GET` | `/api/topics/canonical`【v1.1】 | 主題身分清單與待人工覆核的候選合併（§3A.3 第 3 條） |

`/api/scan/baseline-status` 存在的理由：使用者需要知道「還要幾週，時事那一軌才會開始有意義」。把它藏起來，就會有人在第 2 次掃描時把絕對報導量當成升溫在讀。

**【v1.1】它回傳的是跨度，不是次數，而且 UI 不得自行推算。** §1.1.1 的錯誤（「6 次 = 3 週期」）正是在文件端自行推算出來的；把推算集中在後端一處，這類錯誤就只會發生一次。

### 10.2 畫面（新增第 7 個頁簽「掃描」）

四塊，順序即閱讀順序：

1. **這次掃了什麼** — 方向、地區、平台、種子詞、新聞查詢、樣本數、耗時。**先講範圍再講結論**，因為範圍決定了結論的效力。
2. **證據四象限** — §5.2 的 2×2，四格都可點開
3. **主題清單** — K 個主題，每個展開完整證據鏈（來源影片、樣本內百分位、`channelsAboveCut / channelsRepresented`、報導媒體、可移植性分類）；旁邊並列**未分層的原始排名**，下方是「超出名額的 domain」（§7.3.1）
4. **結合建議** — 方向層簡報（`scored: false`）＋ 該方向 KOL 的既有引擎評分

### 10.3 用詞規範（延續 `docs/11` §2.8）

| 禁止 | 改用 |
|---|---|
| 熱度、熱門度（Track B） | 報導覆蓋度 |
| 正在紅、爆紅、升溫、新趨勢 | 相對於自身基準偏高／樣本內排名前段 |
| 預測、會紅、潛力股 | 候選、值得看、篩選後 |
| 「3 倍以上算離峰」 | 「這批 312 支裡排名前 5」 |
| **「這是離峰值」【v1.1】** | **「在本次 312 支樣本中排名前 4%」**——§3.4.2：系統不宣稱哪支「是」離峰值 |
| **「已做年齡校正」【v1.1】** | **「頻道相對候選，未做年齡校正」**——§3.2 |
| **`GLOBAL` 標成「全球」【v1.1】** | **「英語圈（US 為主）」**——見下 |

**【v1.1】`GLOBAL` 的標籤要在 API 與 UI 一起改，不能只留一行 note。** 這一區實際上是英語世界、且以 US 為 proxy（種子詞、新聞查詢、時區都是）。`persona-directions.json` 裡寫了 note，但**使用者看到的是標籤，不是 note**——留著「全球」這個字，就會有人把它讀成世界樣本。

## §11 先驗常數清單

**【v1.1 移動】常數已從 `kols/scoring-config.json` 移到 `kols/discovery-config.json`。**

理由（Review P1-2）：本規格反覆強調「這不是評分」，但常數卻放在 `scoring-config.json` 裡——**語意上已經開始耦合**。而且 `getConfig()` 是評分引擎的入口，把 discovery 常數塞進去，遲早有人在評分路徑上讀到它。

| 常數 | 初值 | 性質 | 怎麼被推翻 |
|---|---|---|---|
| `windowMonths` | 6 | **使用者設定**，不是宣稱 | 使用者改 |
| `topK` | 3–10 | **使用者設定** | 使用者改 |
| `defaultCutPercentile`【v1.1】 | 前 10% | **檢視預設值**，不是門檻 | 使用者當場移動；§3.4.2 |
| `maturityDays` | 14 | **prior，編的** | `videoObservations` 累積後可看出成長曲線在第幾天轉平（§3.2 第 4 點） |
| `minBaselineVideos` | 8 | **prior，編的** | 用留存樣本回算：中位數在樣本數多少時才穩定 |
| `baselineRecentPosts`【v1.3 改名】 | 30 | **實測口徑修正**——actor 回的是「最近 N 篇」不是「最近 180 天」。同樣 30 篇，發文頻繁的帳號覆蓋 61 天、稀疏的覆蓋 297 天（§3.7.3） | 用留存樣本回算中位數在幾篇時穩定 |
| `madNormalConstant` | 1.4826 | **不是 prior**——具名慣例（Rousseeuw & Croux 1993） | 不需要校準 |
| `newsWindowDays`【v1.1 降級】 | 7 | **讀取時的查詢參數**，不再寫進資料 | §4.4-2 改存 article-level 之後，它可以隨時改、可以並排比較 |
| `requiredWeeklyCycles` | 3 | **單一 source of truth**，兩軌引用同一份 | 已有規格 |
| `maxChannelFetches`【v1.3 定值】 | 100 | **成本上限**。實測每作者 21.6 秒 → 100 個 = **36.1 分鐘** | 實測 Apify 計費後再調 |

**【v1.1】`calibration` 拆成逐項，不再只有一個總 status。** `maturityDays` / `minBaselineVideos` / `newsWindowDays` 的校準證據完全不同——`maturityDays` 靠影片觀看軌跡、`minBaselineVideos` 靠回算中位數穩定性、`newsWindowDays` 靠 article-level 重算。一個共用的 `status: 'calibrated'` 會讓其中一項被校準時，看起來三項都被校準了。

**【v1.1】批准旗標拆成兩個**（§4.3）：`timeSeries.topicHeat.approved` 與 `timeSeries.newsCoverage.approved`。

**在對應的 `calibration.*.status` 變成 `calibrated` 之前，任何文件、UI 或對外說明都不得暗示這些數字有理論根據。** 這條與 `scoring-config.json` 對 `floor` 的既有警語逐字對應。

## §12 這份規格知道自己有哪些問題

誠實列出，不藏在實作裡：

1. **~~§3.7 的頻道基準抓不到~~【v1.3 · 已實測，解除】** profile actor 通過：五個帳號全部 `viewsCoverage 1.0`、`staysOnProfile true`、篇數高於門檻。頻道中位數算得出來，主判準成立（§3.7.3）。`docs/15` §2.2 的三個備案都不需要動用。
2. **~~半年窗到底抓不抓得到~~【v1.2 · 已實測，解除】** TikTok 觸及數年、180 天內佔 82.7%，半年窗成立。**但只在 TikTok**：Instagram 實際只覆蓋約 25 天，Threads 的時間戳原本全部解析失敗（§3.7.1、§3.7.2）。所以這個名字保留，代價是 Track A 只剩一個平台。
3. **~~§4.1 的 RSS 端點未實機驗證~~【v1.3 · 已實測，解除】** 七區 Google News 全通、免 key 確認。但發現要走 `rss/search` 不是主題 feed（差三十倍觸及），且 Yahoo 只在 TW／HK 成立（§4.1.1–4.1.3）。
4. **【v1.1】年齡偏誤未解決，只是被量測與命名。** §3.2 選了「承認做不到」而不是硬做一個 age band 或 `views/days`。所以在 `videoObservations` 累積出成長曲線之前，這份清單**確實會偏向較舊的影片**，只是偏多少看得見。
5. **`maturityDays = 14` 與 `minBaselineVideos = 8` 是編的。** 已標 prior、已寫明推翻路徑，但推翻路徑要跑滿數週才有資料。這段期間它們就是在起作用。
6. **【v1.1】`canonicalTopic` 的第 3 條規則會產生人工佇列。** 實體交集只標候選、不自動合併（§3A.3），代價是有人要去看那個佇列。佇列沒人看，主題身分就會一直碎著——而碎掉的後果是 `channelsAboveCut` 永遠是 1。這是**流程上的依賴，不是技術問題**，但它會決定這套東西好不好用。
7. **政治型方向目前沒有任何 KOL。** 掃描跑得起來，但輸出只會是題目盤點。這是使用者的裁示點，不是系統缺陷。
8. **【v1.1 改】`health` scoring domain 已移出本規格**（§2.3）。代價是健康型方向的題目會落進 `life` 的 `axisDemand`，`fit` 這一維在這個方向上比較鈍。回應帶 `domainFallback: true`。
9. **~~成本尚未估~~【v1.3 · 已量耗時】** 每作者 21.6 秒，100 個投影 36.1 分鐘。**實際計費仍未知**——要看 Apify console，探測拿不到。
10. **【v1.3 新增】0-8 未觀測。** 五個受測帳號都是公開且正常的，所以「私人／已刪除／限區影片怎麼標」沒有答案。這不是「actor 不標記」，是這批沒有可標記的。要判定得刻意找一個已知的私人帳號來打。
11. **【v1.3 新增】48% 的抽樣 churn 是已量測、未解決的限制。** 它不是 bug，是 TikTok hashtag feed 的行為。設計上已用「單次掃描內的跨頻道重現」繞開（§8.2.2），但跨週的任何宣稱都要打折。
12. **`docs/11` §15 的兩個未決問題仍未決**：`rachel-ong` / `rafael-costa` / `faye-tan` 的可信度型態；以及 `personaFit` 常態性回傳 100 導致 EXPERIMENT 帶樣本稀少。本規格沒有處理，也沒有讓它們變得更糟。
