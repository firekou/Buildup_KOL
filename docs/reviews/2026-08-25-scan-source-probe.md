## §0 結論

| 平台 | 0-4 · 覆蓋 180 天 | 0-5 · 分頁深度 | 能不能做 Track A |
|---|---|---|---|
| **TikTok** | ✅ **可以**，`ageP90` 深達數年 | ⚠️ 加大 limit 增加**密度**不增加**觸及**，觸及在 tier 100 就到頂 | ✅ **可以** |
| **Instagram** | ❌ **不行**，實際只有 ~25 天 | ❌ 加大 limit 只是拿到更多當月貼文 | ❌ 不行 |
| **Threads** | ❌ **無法判定**，actor 回傳的時間戳全部解析失敗 | — | ❌ 不行 |

**「半年內離峰值掃描」這個名字站得住，但只在 TikTok 上。** IG 與 Threads 不能供應半年窗。

這與 `docs/14` §3.7 早先的判斷（只有 TikTok 有可靠的觀看數）**獨立地指向同一個結論**。現在有兩個不同的理由說同一件事，不是同一個理由講兩次。

**額外發現一個既有的生產環境 bug**，見 §4。

## §1 判準（先寫，後看數字）

### 0-4

| 觀察 | 判定 |
|---|---|
| `oldestAgeDays >= 150` 且 `olderThanWindow > 0` | ✅ 真的能翻到半年附近 |
| `oldestAgeDays` 落在 30–150 | ⚠️ 部分覆蓋 |
| `oldestAgeDays < 30` 且 `descRatio >= 0.95` | ❌ 只回「最近 N 筆」 |
| `dated == 0` | ❌ 無法判定 |

### 0-5

比較同平台三個 tier 的 `oldestAgeDays`：往後推 = 分頁有效；幾乎不動 = 沒有深度分頁。

### ⚠️ 這組判準有一個缺陷，實測時才發現

**`oldestAgeDays` 是一個最大值，而最大值只要一筆離群就會說謊。**

Instagram tier 300 回了 `oldestAgeDays = 4339`（一則 2014 年的貼文），照上表會被判成 ✅ 通過。但逐月直方圖顯示 **900 則裡有 892 則在 2026-08**——是 8 則被釘選的 top posts 讓一個 25 天的切片看起來像十二年的觸及。

**判準本身不夠，是靠直方圖才看出真相的。** 這件事寫在這裡而不是默默改掉，因為它就是這個 repo 反覆在防的那類錯：一個看起來精確的數字，其實在描述尾巴不是身體。

**已修：** `describeAges` 補上 `ageP50Days` / `ageP90Days` / `ageP99Days`。`ageP90` 才是「這批資料實際涵蓋多久」的誠實答案。這與離峰值模型選 median/MAD 而不選 mean/SD 是同一個理由——重尾分布裡，極值描述的是尾巴。

## §3 判讀

### 3.1 TikTok：0-4 通過，0-5 部分通過

- **觸及夠深。** `descRatio ≈ 0.50` 表示回傳順序不是由新到舊——它不是「最近 N 筆」的切片。搭配 tier 300 有 150 則落在 180 天之外，這是真的能翻到舊內容。
- **窗內佔 82.7%**（717/867）。所以半年窗對 TikTok 主要是一道**篩選**，不是一道**觸及障礙**。這是好消息：不必為了湊滿半年而把 limit 開到很大。
- **0-5 的限制：** tier 100 與 tier 300 的 `oldestAt` **完全相同**（`2020-01-28T13:35:38`）。加大 limit 讓樣本變密，但最舊的那一筆不動——代表 actor 可及的池子有一個固定的底，tier 100 就已經摸到。

  實務後果：**要更舊的內容，不能靠加大 limit，要換種子詞。**

- **`resultsPerPage` 是每個 hashtag 各自的數量，不是總數。** 三個種子 tag → `fulfilledRatio` 穩定在 ×3。現行 `fetchRegionTopics` 傳 `limit: Math.max(limit*4, 40)`，實際拿回的是那個數字的三倍。這不是 bug，但成本估算要用對的乘數。

### 3.2 Instagram：0-4 不通過

- **`descRatio 0.93–0.96` 是「最近 N 筆」的簽名**——回傳順序幾乎單調由新到舊。
- 三個 tier 的實際觸及：2.6 天 → 23.9 天 → **仍然是 2026-08 一個月**。
- 那 8 則舊貼文分散在 2014、2019、2025-07、2026-07，中間整整幾年是空的。**真正在翻歷史的資料不會長這樣**——那是 hashtag 頁的 top posts。

**判定：Instagram 提供的是「當月最新」，不是半年窗。** 就算把 limit 開更大，多拿到的還是當月的。

### 3.3 Threads：無法判定，而且原因是我們自己的 bug

`dated = 0`：**每一則的時間戳都解析失敗。** 見 §4。

修掉之後這一軌可以重測，但即使時間戳能解析，Threads 對 Track A 仍然不利——`view_count` 不穩定（`docs/14` §3.7 早已記錄），而離峰值分析需要觀看數。

## §4 順帶發現：Threads 的時間戳從來沒有被解析成功過

`watcher.data~search-threads-by-keywords` 的 `created_at` 是 **Unix epoch 整數（秒）**，不是 ISO 字串：

```
1787631594  →  2026-08-25T04:19:54.000Z
```

但 `toPost` 的 threads 分支是 `timestamp: item.created_at ?? null`，接著 `aggregatePostsToTopics` 做 `Date.parse(post.timestamp)`。`Date.parse` 收到數字會先轉成字串 `"1787631594"`，那不是合法日期 → **NaN**。

後果：**這個連接器上線以來，每一則 Threads 貼文都被當成沒有時間戳。** `recencyRatio48h` 對任何由 Threads 貼文帶進來的標籤，一律算成「沒有一則是最近的」。

這個 bug 不會噴錯、不會讓任何測試變紅，因為缺失的日期會靜靜地變成一個 0。

**探測之所以抓到它，只因為 `describeAges` 把 `undated` 當成一個獨立的數字回報**，而不是讓它消失在 0 裡面。這正是 `docs/11` §0 紀律 3 想要的東西——只是這次是規格自己的量測工具救了規格。

**已修：** 新增 `toIso()`，三個平台的時間戳都走同一支正規化（字串 ISO、字串數字、秒級 epoch、毫秒級 epoch 都吃）。秒／毫秒的判別用 `< 1e11` 而不是數位數，這樣對未來日期也正確。

## §5 這次不宣稱的事

- **只跑了 TW。** 其他地區的種子詞不同，覆蓋能力可能不同，**不外推**。
- **不是 0-9（重跑穩定度）。** 每個 tier 只跑一次。TikTok tier 100 與 tier 300 的 `oldestAt` 相同，隱約支持「同一 query 的池子穩定」，但一次觀察不足以下結論。
- **不是 0-10（成本）。** `elapsedMs` 有記（最慢 119 秒），但實際 Apify 計費要看 console，這裡拿不到。
- **Threads 修好後未重測。** 修的是解析，不是 actor；重測要再花一次錢，留給下一輪連同 0-1～0-3 一起跑。

## §6 對規格的影響

1. **`docs/14` §3.7 的平台建議從「建議」升級為「實測結論」。** TikTok 是三個平台裡唯一能同時提供半年窗與觀看數的。
2. **半年窗這個名字保留**，但要加註「只在 TikTok 成立」。
3. **`docs/15` 批次 0 的裁示點 #2（窗長改多少）不需要動用**——TikTok 撐得住 180 天。
4. **新增一個限制到 §8.2 的偏誤表：** 要更舊的內容只能換種子詞，不能加大 limit。這讓「種子詞邊界」這條偏誤比原本更強——它不只決定看到什麼題材，也決定看得回多久。
5. **成本乘數要用 ×3**（每個種子 tag 各自計數），不是 ×1。
